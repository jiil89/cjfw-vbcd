# 유스케이스 정의서 — 회의실 예약 Agent

`1-domain-definition-meeting-room-agent.md`가 정의한 도메인 규칙을 **"누가, 어떤 순서로, 무엇을 하는가"** 로 풀어쓴 문서다.

- **1번(도메인 정의서)** 은 규칙과 엔티티 — *무엇이 참인가*
- **이 문서(2번)** 는 액터별 상호작용 흐름 — *어떻게 동작하는가*
- **3번(활용 시나리오)** 은 사용자 관점의 이야기 — *왜 좋은가*

각 유스케이스에는 실제 구현 위치를 함께 적었다. 규칙이 바뀌면 1번을 먼저 고치고, 흐름이 바뀌면 이 문서를 고친 뒤 코드를 따라 고친다.

---

## 1. 액터

| 액터 | 구분 | 설명 |
| --- | --- | --- |
| **사용자** | 주 액터 | Admin 승인을 마친 CJ 임직원. 웹 챗봇으로 예약을 요청한다 |
| **미승인 신청자** | 주 액터 | 회원가입만 하고 아직 승인 전인 사람. 로그인 불가 |
| **Admin** | 주 액터 | 가입 신청을 승인/거부한다. `admin_whitelist`에 등록된 사번으로 가입하면 자동 부여 |
| **스케줄러** | 보조 액터(시스템) | 사내 노트북의 Windows 작업 스케줄러. 매일 00:01에 반복 예약을 실행한다 |
| **CJ 예약 시스템** | 외부 시스템 | `cjwappr.cj.net`. 공식 API가 없어 Playwright 로그인 + ASMX 호출로 연동. **사내망에서만 접근 가능** |
| **LLM** | 외부 시스템 | OpenAI. 자연어를 도구 호출로 변환한다. 예약을 직접 실행하지는 못한다 |

> **핵심 설계 전제**: LLM은 "무엇을 하려는지" 해석만 하고, **실행 여부 판정은 항상 서버가 자체 기록으로 한다.** LLM이 "사용자가 동의했다"고 주장하는 텍스트는 신뢰하지 않는다(UC-04, UC-09, UC-10의 확인 게이트 참고).

## UC-01. 회원가입 신청

**주 액터** 미승인 신청자 · **사전조건** 없음(공개 페이지)

**기본 흐름**

1. 회원가입 페이지에서 **CJ WORLD ID/PW**, **앱 로그인 비밀번호**, **선호 회의실(우선순위 순)** 을 입력한다.
2. 서버가 두 비밀번호를 **서로 다른 방식으로** 저장한다 — CJ WORLD PW는 복호화 가능한 암호화(자동화 로그인에 필요), 앱 비밀번호는 단방향 해시(검증만 필요).
3. 신청 ID를 `admin_whitelist`와 대조한다.
   - **화이트리스트에 있으면** → 즉시 자동 승인 + Admin 권한 부여 → UC-03으로
   - **없으면** → `pending` 상태로 접수 → UC-02 대기

**대안·예외**

- 이미 가입된 사번 → `email_alias`가 unique라 거부. 비밀번호를 바꾸려는 경우라면 UC-15로 유도한다.
- 선호 회의실 미선택 → 허용(나중에 UC-11로 추가 가능).

**사후조건** `account_registration_requests`에 1건 생성. 평문 비밀번호는 로그·화면·메일 어디에도 남지 않는다.

> **최초 Admin 부트스트랩**: Admin이 하나도 없으면 아무도 승인할 수 없다. 이 닭·달걀 문제는 마이그레이션으로 `admin_whitelist`에 최초 사번을 심어 푼다.

## UC-02. 가입 승인 / 거부

**주 액터** Admin · **사전조건** Admin으로 로그인, 대상 신청이 `pending`

**기본 흐름**

1. Admin 패널에서 대기 목록을 확인한다.
2. **승인** → `users` 행 생성 + 신청 시 고른 선호 회의실을 `user_preferred_rooms`로 이관.
   **거부** → 자격증명 즉시 폐기(암호문을 비우고 해시를 삭제).

**대안·예외**

- 이미 처리된 신청을 다시 처리 → DB 함수가 거부한다(`status <> 'pending'`이면 예외).
- **권한 위조 시도** → 승인 함수는 `security definer`이고 anon/authenticated의 EXECUTE 권한이 회수돼 있다. 또한 호출자가 실제 활성 Admin인지 **DB가 직접 재확인**한다 — 서버 코드의 JWT 검사에만 의존하지 않는 이중 방어.

**사후조건** 사용자가 로그인 가능해진다.

## UC-03. 로그인 / 세션 유지

**주 액터** 사용자 · **사전조건** 승인 완료(`status = 'active'`)

**기본 흐름**

1. 사번 + 앱 로그인 비밀번호를 제출한다.
2. 서버가 해시를 검증하고, **CJ 세션을 미리 확보(예열)** 한다.
3. Access Token(15분, 응답 바디) + Refresh Token(7일, httpOnly 쿠키)을 발급한다.
4. Access Token 만료 시 프론트가 `/auth/refresh`로 자동 갱신한다 — 사용자는 7일간 끊김을 느끼지 않는다.

**대안·예외**

- **CJ 로그인 실패 시 로그인 자체를 거부한다.** 앱에는 들어왔는데 예약이 전부 실패하는 상태를 막기 위한 의도적 설계다. 대신 이 경우 로그인 화면에서 바로 UC-15를 할 수 있어야 한다(JWT가 없으므로 본인 확인은 앱 로그인 비밀번호로).
- 승인 대기/거부 상태 → 로그인 거부 + 상태 안내.

**사후조건** 챗봇 이용 가능. Refresh Token 해시가 `refresh_tokens`에 기록되어 서버가 개별/전체 폐기할 수 있다.

## UC-04. 회의실 예약 (해피 패스)

**주 액터** 사용자 · **사전조건** 로그인 상태

**기본 흐름**

1. 사용자가 자연어로 요청한다("내일 오후 2시에 회의실 잡아줘").
2. 정보가 부족하면 Agent가 **날짜·시간 / 인원 / 회의명을 한 번에** 묻는다(하나씩 나눠 묻지 않는다 — 실사용 최대 불만이었다).
3. `check_availability`로 조회하고 **선호 회의실을 우선 제시**한다. 선호가 전부 찼으면 되묻지 않고 **대안 목록을 즉시 함께** 보여준다.
4. 사용자가 목록에서 하나를 고른다.
5. 예약이 확정되고 결과를 안내한다. **이때 저장된 회의명도 함께 밝힌다.**

**확인 게이트 (중요)**

실제 CJ에 쓰는 도구는 `confirm_*`이며 `confirmationToken`을 요구한다. 토큰은 `propose_*`가 발급하고, **같은 턴에 발급된 토큰은 거부된다** — 사용자의 다음 메시지를 반드시 거치게 하는 장치다.

단, **직전 턴에 서버가 실제로 보여준 목록에서 골랐다면** 그 선택 자체가 명시적 동의이므로 확인을 생략하고 즉시 실행한다. 이 판정 근거는 서버가 기록한 `offeredSlots`뿐이며, LLM의 주장은 근거가 되지 않는다.

**대안·예외**

- 회의명을 끝내 안 주면 → 기본 제목으로 진행. **맥락에서 그럴듯한 이름을 지어내지 않는다**(실사용에서 "AI챗봇 테스트"가 임의 생성돼 실제 CJ에 올라간 사례가 있다).
- 범위 밖 요청(없는 층, 운영시간 외, 7일 초과, 장비 조건) → 시도하지 않고 명확히 안내.
- 2시간 초과 → UC-07로 분기.
- 저장 직전 선점당함 → 실패 사유와 함께 재조회 제안.

**사후조건** CJ에 예약 생성 + `reservations` 행 저장.

## UC-05. 조건 검색 (인원수·층)

**주 액터** 사용자 · **사전조건** 로그인 상태

**기본 흐름**

1. "8명 들어가는 방 있어?", "12층에 빈 회의실?" 처럼 조건을 함께 묻는다.
2. 가용성 결과에 회의실 수용인원·층 정보를 결합해 필터링한다.
3. 요청한 층에 자리가 없으면 **"다른 층 찾아드릴까요?"라고 되묻지 않고** 같은 시간대의 다른 층 결과를 바로 함께 제시한다(이미 조회가 끝난 결과라 되물으면 한 턴만 낭비된다).

**대안·예외** 시간을 안 주고 날짜만 준 경우 → 기본값을 지어내지 않고 시간대를 먼저 묻는다. 지어낸 시간으로 조회한 카드를 사용자가 그대로 확정하면 원치 않는 시간에 예약될 수 있다.

**사후조건** 없음(조회 전용).

## UC-06. 이력 기반 추천

**주 액터** 사용자 · **사전조건** 로그인 상태

**기본 흐름**

1. "자주 쓰던 데로 잡아줘" 같은 이력 기반 표현을 쓴다.
2. 등록된 선호 회의실이 있으면 그것을 1순위로 쓴다.
3. 없으면 취소되지 않은 과거 예약을 회의실별로 집계해 상위 후보를 제시한다.

**사후조건** 없음(조회 전용). 이후 UC-04로 이어진다.

## UC-07. 긴 회의 분할 예약 (2시간 초과)

**주 액터** 사용자 · **사전조건** 로그인 상태, 요청 길이 > 120분

**배경** CJ는 "같은 사람 + 같은 회의실" 하루 합계 2시간을 넘기지 못하게 막는다. 따라서 3시간 연속 회의는 **서로 다른 회의실 여러 개를 시간이 이어지도록** 잡는 수밖에 없다.

**기본 흐름**

1. 세그먼트를 계산한다 — 앞에서부터 최대 120분씩 채우고 나머지를 마지막에 배정(180분 → 120+60).
2. 세그먼트마다 회의실을 배정하되 **같은 회의실을 두 번 쓰지 않고**, 이동 편의를 위해 가능하면 같은 층/인접 층을 고른다.
3. **전체 계획을 한 번에** 보여주고 한 번만 확인받는다(세그먼트별로 따로 묻지 않는다).
4. 순차 실행해 세그먼트마다 별도 예약을 생성한다.

**대안·예외 — 부분 실패 보상**

중간 세그먼트가 실패하면(그 사이 선점 등) **이미 만든 앞 세그먼트를 자동 취소**하고 실패를 알린다. CJ에는 여러 건을 묶는 트랜잭션이 없으므로 "전부 성공 또는 전부 취소"를 애플리케이션이 보장한다.

**사후조건** N개의 `reservations` 행이 **같은 `reservation_request_id`** 를 공유한다. 조회 시 이 값으로 묶어 하나의 회의처럼 보여준다.

## UC-08. 내 예약 조회

**주 액터** 사용자 · **사전조건** 로그인 상태

**기본 흐름**

1. 챗봇으로 묻거나, 사이드바 "오늘 예약"에서 확인한다.
2. 같은 `reservation_request_id`를 공유하는 분할 예약은 **하나로 묶어** 안내한다("14:00~17:00 연속 회의, 2개 회의실").
3. 답변에는 **항상 어느 날짜 기준인지 밝힌다** — 대화가 길어지면 사용자가 조건을 바꿔 물은 걸 잊고 "아까는 없다더니?"로 오해한다(실사용 발생).

**사후조건** 없음(조회 전용).

## UC-09. 예약 변경

**주 액터** 사용자 · **사전조건** 로그인 상태, 대상 예약 존재

**기본 흐름**

1. "화요일 3시 거 다른 데로 바꿔줘"처럼 요청한다.
2. `find_reservation_candidates`로 대상을 좁힌다. 이때 **대화에 이미 나온 날짜/시간/회의실을 최대한 재사용**한다.
3. 후보가 정확히 1건이면 되묻지 않고 진행, 2건 이상이면 목록을 보여주고 반드시 되묻는다.
4. 새 조건으로 재조회 후 변경을 실행한다.

**대안·예외**

- **CJ `checkRoom`을 신뢰하지 않는다.** 이미 점유된 슬롯에 대해 "가능"으로 거짓 응답하는 것을 실측 확인했다. 변경은 "원본 취소 → 재생성" 전략이라 이 거짓말이 **원본을 먼저 지워버리는** 사고로 이어진다. 따라서 삭제 전에 **자체 가용성 판정으로 한 번 더 검증**하고, 불가하면 원본을 건드리지 않은 채 거절한다.
- 변경 실패 시 → 사유를 그대로 전하고 그 시간에 가능한 다른 회의실을 바로 제시한다. 원본은 유지된다.
- 분할 예약의 변경은 미지원 → 취소 후 재예약으로 안내.

**사후조건** 성공 시 새 예약 확정, 실패 시 원본 유지.

---

## UC-10. 예약 취소

**주 액터** 사용자 · **사전조건** 로그인 상태, 대상 예약 존재

**기본 흐름**

1. 취소를 요청한다.
2. 대상이 1건으로 특정되면 **다시 묻지 않고 즉시 취소**한다.
3. CJ에서 취소하고 `reservations.status`를 `cancelled`로 갱신한다.

**대안·예외**

- 후보가 여러 건 → 반드시 되묻는다.
- **분할 예약이면 "전체 취소"인지 "일부만"인지 반드시 확인한다.** 기본값을 임의로 정하지 않는다 — 이 확인은 위 "즉시 실행" 규칙의 **예외로 항상 유지**된다.

**사후조건** 해당 예약이 CJ와 DB 양쪽에서 취소 상태가 된다.

## UC-11. 선호 회의실 관리

**주 액터** 사용자 · **사전조건** 로그인 상태

**기본 흐름**

1. **추가/삭제**는 챗봇으로 즉시 처리한다("선호 회의실에 14F-2 추가해줘"). 앱 내부 설정이라 되돌리기 쉬우므로 확인 2단계를 거치지 않는다.
2. **목록 조회는 채팅으로 지원하지 않는다.** "내 선호 회의실 뭐야?"라고 물으면 **첫 답변부터** 우측 패널을 안내한다 — "지원 안 함"이라고만 답하고 되묻게 만들지 않는다(실사용 불만).

**대안·예외** 최대 5개까지. 초과 시 거부하되, **이미 등록된 회의실을 다시 추가하는 건 상한과 무관하게 통과**시킨다(어차피 변화가 없는데 막으면 혼란만 준다).

**사후조건** `user_preferred_rooms` 갱신. 이후 UC-04의 우선순위에 반영된다.

## UC-12. 반복 예약 규칙 등록

**주 액터** 사용자 · **사전조건** 로그인 상태, **UC-14 동의 유효**

**배경** CJ가 7일 뒤까지만 받으므로 "3개월치 매주 화요일"을 미리 넣을 수 없다. 그래서 규칙만 등록해두고 **예약 창이 열리는 순간 자동으로 잡는다**(UC-13).

**기본 흐름**

1. 사이드바(모바일은 "내 정보" 시트) "매주 반복 예약"을 연다.
2. 동의가 없으면 동의 게이트가 먼저 뜬다 → UC-14.
3. 요일 / 시작·종료 시각 / 회의명 / **회의실 1~3순위**를 입력한다.
4. 저장한다.

**대안·예외**

- 동의 없이 생성 시도 → 400 `CONSENT_REQUIRED`.
- 30분 단위·운영시간·2시간 상한 위반 → 거부(예약 시점과 같은 규칙을 등록 시점에 미리 적용).

> **"반복 대상 회의실"은 "선호 회의실"과 다르다.** 선호 회의실은 사용자 전역 취향(추천 정렬용)이고, 이건 **이 규칙 하나를 실행할 때의 시도 순서**다. 규칙마다 다를 수 있어 별도 테이블로 둔다.

**사후조건** `recurring_reservation_rules` + `recurring_reservation_rule_rooms` 생성.

## UC-13. 반복 예약 자동 실행

**주 액터** 스케줄러(시스템) · **사전조건** 노트북 가동 + 사내망 연결

**기본 흐름**

1. 매일 **00:01**에 실행되어 **대상일 = 오늘(KST) + 7일** 을 계산한다.
2. 대상일의 요일과 일치하는 **활성 규칙**을 찾는다.
3. 규칙마다 **순차적으로**(병렬 금지) 처리한다.
   - 이미 같은 `(규칙, 대상일)` 실행 기록이 있으면 건너뛴다 — **멱등성**.
   - 사용자가 비활성이거나 **동의가 철회됐으면 건너뛴다** — 실행 시점 재확인.
   - 1순위부터 차례로 예약을 시도하고, 성공하면 중단한다.
4. 결과를 `recurring_reservation_runs`에 남긴다. 사용자는 사이드바에서 확인한다.

**대안·예외**

- **CJ 로그인 실패 시 나머지 순위를 시도하지 않고 즉시 중단한다.** 매 시도마다 재로그인하므로 그냥 넘어가면 한 규칙에서 실패 로그인이 최대 3회 쌓여 **CJ 계정 잠금 정책을 자극**한다.
- 1~3순위 전부 만석 → 실패로 기록.
- **노트북이 그 시각에 꺼져 있으면 그날 실행이 사라진다.** 작업에 `StartWhenAvailable`을 켜서 켜진 직후 따라잡게 해야 한다(2026-08-19에 실제로 하루치가 누락됐다).

**병렬 금지 이유** 사용자마다 Playwright 브라우저 + CJ 로그인이 하나씩 뜬다. 동시에 여러 계정이 로그인하면 CJ가 이상 트래픽으로 감지할 가능성이 있어, 규칙 사이에 짧은 지연을 두고 하나씩 처리한다.

**사후조건** 성공 시 실제 CJ 예약 + `reservations` 행 생성.

## UC-14. 에이전트 자동 실행 동의 / 철회

**주 액터** 사용자 · **사전조건** 로그인 상태

**배경** UC-13은 사용자가 앱에 없을 때 서버가 **사용자의 CJ 계정으로 대신 로그인**한다. 기존의 "사용자 요청 시에만 복호화"보다 권한이 확대되므로 명시적 동의가 필요하다.

**기본 흐름 (동의)**

1. 동의 문구를 읽고 체크한다 — 대상일 7일 전에 에이전트가 대신 로그인해 예약한다는 사실, 서버가 꺼져 있으면 실행되지 않을 수 있다는 한계를 명시한다.
2. 동의 시각이 기록된다.

**기본 흐름 (철회)**

1. 철회를 요청한다.
2. 철회 시각이 기록되고, **그 사용자의 모든 반복 규칙이 즉시 비활성화된다.**

**3중 게이트**

① 규칙 생성 시 동의 확인 → ② 자동 실행 때마다 재확인 → ③ 철회 시 전체 즉시 비활성화

추가로 **규칙을 다시 켜는 것(활성 토글)도 동의를 재확인한다.** 끄는 건 항상 허용한다. 이 검사가 없으면 철회 후에도 토글만으로 재활성화되는 구멍이 생긴다(실제로 있었던 결함).

**사후조건** `users`의 동의/철회 시각 갱신.

## UC-15. CJ WORLD PW 재등록

**주 액터** 사용자 · **사전조건** 없음(로그인 전에도 가능)

**배경** CJ WORLD PW는 사내 정책상 주기적으로 만료된다. 우리가 보관한 암호문이 낡으면 **그 사용자에게는 앱 전체가 멈춘다.** 사번이 unique라 재가입도 막히므로, 이건 편의 기능이 아니라 **필수 복구 경로**다.

**기본 흐름**

1. 진입 경로는 상태에 따라 둘이다.
   - 아직 로그인이 되면 → 사이드바에서
   - **이미 로그인이 막혔으면 → 로그인 화면에서 직접.** 이때 본인 확인은 JWT가 아니라 **앱 로그인 비밀번호**로 한다.
2. 새 PW로 **실제 CJ 로그인을 시도해 검증**한다. **검증에 성공한 값만 저장한다** — 검증 없이 저장하면 오타 하나로 모든 동작이 죽는데 사용자는 원인도 모른다.
3. 저장 후 옛 PW로 맺어둔 **CJ 세션 캐시를 즉시 버린다.**

**사후조건** 이후 모든 CJ 자동화가 새 자격증명으로 동작한다.

## UC-16. 앱 로그인 비밀번호 변경

**주 액터** 사용자 · **사전조건** 현재 비밀번호를 알고 있음

**기본 흐름**

1. 현재 비밀번호를 확인한 뒤 새 값으로 교체한다.
2. **그 사용자의 Refresh Token을 전부 폐기**해 다른 기기의 로그인 상태를 끊는다.

**대안·예외** 비밀번호를 **잊어버린** 경우의 자가 재설정은 **미지원** — 메일 발송 수단이 없어 본인 확인을 할 방법이 없다. 현재는 Admin 대행만 가능하다.

## 3. 모든 유스케이스에 적용되는 상위 원칙

1. **범위 밖이면 시도하지 않는다.** 도구 호출 전에 "정의된 능력과 제약(상암S시티 고정, 3F·12~16F, 07:00~19:00, 30분 단위, 동일 회의실 하루 2시간, 오늘~7일) 안인가"를 먼저 판단한다. 벗어나면 명확히 안내하고, 애매하면 추측하지 말고 되묻는다. **이 원칙은 여기 없는 새로운 요청에도 그대로 적용된다.**
2. **되묻지 않는 것이 기본, 변경·취소만 예외.** 조회·추천은 대안을 바로 제시한다. 되돌리기 어려운 액션만 모호할 때 확인한다.
3. **실행 판정은 서버가 한다.** LLM이 생성한 텍스트는 동의의 근거가 될 수 없다.
4. **자격증명은 CJ 자동화 계층 밖으로 나가지 않는다.** 복호화된 CJ 비밀번호를 상위 계층이 넘겨받지 않는다.
5. **처리 중임을 항상 보여준다.** 헤드리스 브라우저를 매번 띄우므로 응답까지 몇 초가 걸린다.
