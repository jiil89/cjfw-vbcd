# E2E 테스트 결과 — Vercel 실습용 배포 (2026-08-21)

**대상**: `https://cjfw-vbcd-f7ff.vercel.app` (학습용 Vercel 배포, DB는 실습용 Supabase 프로젝트 `cjfw-vbcd-study`에 연결. 실제 운영 DB/CJ 시스템과는 완전히 분리됨)

**전제**: CJ 사내 예약 시스템은 사내망 전용이라 Vercel(클라우드)에서는 도달할 수 없다. 그래서 "로그인 이후(CJ 세션 확보가 필요한 모든 기능)"는 이 배포에서 원천적으로 재현 불가능하며, 이는 버그가 아니라 구조적 한계다.

## 1차 실행

| # | 시나리오 | 결과 | 비고 |
|---|---|---|---|
| 1 | 프론트 화면 로드(`/`) | ✅ 200 | 정적 파일 서빙, 백엔드 무관 |
| 2 | 헬스체크(`/health`, 실제 DB 연결) | ✅ `{"status":"ok"}` | 실습용 Supabase에 실제 연결 성공 |
| 3 | 회의실 공개 조회(`/rooms`) | ✅ 200, `[]` | 마이그레이션만 적용, 방 데이터 시드는 안 해서 빈 배열이 정상 |
| 4 | 화이트리스트 계정(jiil) 가입 → 자동승인 | ✅ 201 `auto_approved` | `admin_whitelist`에 seed된 계정이라 자동승인 로직 탐 |
| 5 | 같은 계정 중복 가입 방지 | ✅ 409 `EMAIL_ALIAS_TAKEN` | unique 제약 + 서비스 로직 검증 정상 |
| 6 | 비화이트리스트 계정 가입 → 승인대기 | ✅ 201 `pending` | 화이트리스트 미해당 시 분기 정상 |
| 7 | 로그인(jiil) | ⚠️ 401 `CJ_LOGIN_FAILED` | **CJ 사내 시스템이 사내망 전용이라 Vercel에서 도달 불가 — 구조적 한계, 코드/DB 문제 아님** |
| 8 | 인증 없이 Admin API 접근 차단(`/admin/locked-users`) | ✅ 401 `UNAUTHORIZED` | JWT 미들웨어 정상 |

DB 조회로도 실제 반영 확인: `users` 테이블에 `jiil / active / is_admin=true` 행 생성됨.

## 2차 실행 (CJ 도메인/코드값을 하드코딩에서 필수 환경변수로 리팩터링한 뒤 회귀 확인)

| # | 시나리오 | 결과 | 비고 |
|---|---|---|---|
| 1 | 프론트 화면 로드 | ✅ 200 | |
| 2 | 헬스체크(DB 연결) | ✅ `{"status":"ok"}` | `CJ_PORTAL_BASE_URL` 등 5개 신규 필수 환경변수 추가 이후에도 **부팅 정상** |
| 3 | 회의실 공개 조회 | ✅ 200, `[]` | |
| 4 | 기존 계정(jiil) 중복 가입 방지 | ✅ 409 | 1차 실행 데이터가 유지돼 회귀 확인용으로 유효 |
| 5 | 신규 비화이트리스트 계정 가입 | ✅ 201 `pending` | |
| 6 | 로그인(jiil) | ⚠️ 401 `CJ_LOGIN_FAILED` | 1차와 동일한 예상된 실패 — 리팩터링이 이 동작을 안 바꿨음을 확인 |
| 7 | 인증 없이 Admin API 차단 | ✅ 401 | |

세션 내 세 번째 배포(회사명 도메인 프로즈 제거 후, `session.ts` 쿠키 domain 비교 로직을 `config.cjBaseUrl` 기반으로 변경)에서도 `/health` 재확인 결과 동일하게 `{"status":"ok"}`.

## 결론

- 가입 → 승인(자동/대기) → DB 반영 → 인증 가드까지의 흐름은 전부 정상.
- "로그인 이후" 흐름(CJ 세션 확보가 전제되는 모든 기능)은 이 실습 배포 구조상 검증 불가 — 실제 검증은 사내 노트북 배포에서만 가능(`docs/laptop-server-setup.md` 참고).
- 두 차례의 코드 리팩터링(CJ 접속정보 env var화, 도메인명 일반화) 모두 배포/DB 연결에 회귀를 일으키지 않았음을 확인.
