# 도메인 정의서 — 회의실 예약 Agent

## 0. 문제 상황 (왜 이 서비스가 필요한가)

- 업무 특성상 **미팅을 매우 자주** 해야 한다.
- 인원수/시간대에 맞는 회의실을 **빠르게** 잡아야 할 때가 많은데, 지금은 예약 화면을 직접 열어서 **언제 어디가 비어있는지 하나하나 눈으로 확인**하고, **직접 타이핑해서 저장**해야 한다 — 이 과정 자체가 번거롭고 느리다.
- 이 지연이 실제로 **관련 업무를 하루이틀 늦추는 경우**도 있다 — 단순 불편이 아니라 실제 업무 손실로 이어짐.
- 그래서 필요한 조건(인원수/시간대 등)에 맞는 회의실을 **빠르게 확인하고, 쉽게 예약**할 수 있는 서비스가 필요하다. 이게 이 프로젝트의 존재 이유다.

## 1. 프로젝트 개요

- 서비스 설명: 사용자가 챗봇(1차 채널: 웹 챗봇, 텔레그램/카카오톡은 추후 확장)에 목적·날짜·시간대를 입력하면, Agent가 사내 회의실 예약 현황을 확인해 가능한 회의실/시간을 안내하고, 사용자 요청에 따라 예약을 자동으로 확정한 뒤 결과를 피드백하는 시스템.
- 주요 사용자(액터):
  - 직원(요청자): 챗봇으로 예약을 요청/변경/취소하는 사람
  - Agent(시스템): 가용성 조회, 예약 확정, 충돌 시 대안 추천, 결과 피드백을 수행하는 주체
  - (참고) 회의실 관리자: 이번 범위에서는 승인 절차 없음(자동 확정) → 별도 액터로 개입하지 않음
  - **Admin(서비스 관리자)**: 직원의 사내 계정 시스템 계정 등록 요청을 검토·승인/거부하는 사람. 회의실 예약 자체에는 관여하지 않고, **최초 계정 등록 단계에서만** 개입함

## 2. 핵심 업무 프로세스

### 사용자 온보딩(회원가입 → 승인 → 로그인) 프로세스 — 예약 이용 전 최초 1회

**[변경됨]** 1차 채널이 웹 챗봇으로 바뀌면서, 신원 확인 방식도 텔레그램 딥링크에서 **자체 회원가입/로그인(이메일·비밀번호 기반 JWT)** 으로 바뀌었다 (`docs/4-prd.md` "인증/보안" 참고). 텔레그램 딥링크 방식은 텔레그램 채널이 실제로 추가될 때 별도 신원 확인 수단으로 재검토한다.

1. 사용자가 **회원가입 웹페이지**(= 기존 "등록 웹페이지")에 접속해 사내 계정 시스템 ID/PW, **선호 회의실(우선순위 순서)**, 그리고 **이 앱 전용 로그인 비밀번호**를 함께 입력해 신청
2. 요청 접수 즉시 두 비밀번호를 각각 다르게 저장한다 — **사내 계정 PW는 복호화 가능한 암호화**(자동화 로그인에 필요), **앱 로그인 비밀번호는 단방향 해시**(로그인 검증에만 필요, 복호화 불필요). 평문은 어떤 단계에서도 로그/화면/메일에 노출하지 않음
3. **Admin 화이트리스트(사전 등록된 사내 계정 시스템 ID 목록) 대조**:
   - 신청한 ID가 화이트리스트에 있으면 → **자동 승인**, 즉시 Admin 권한 부여 + 로그인 가능
   - 화이트리스트에 없으면 → "대기(Pending)" 상태로 접수, 등록된 모든 Admin의 이메일로 **알림 메일**(신청자 정보만 포함, 비밀번호 절대 미포함) 발송 → 메일의 링크는 Admin 웹 패널(로그인 필요)로 연결, 메일 링크 자체로 즉시 승인되지 않음
4. Admin이 웹 패널에 로그인한 상태에서 승인 또는 거부 처리
5. 승인 시: 사용자가 **로그인 페이지**에서 신청 시 설정한 앱 로그인 비밀번호로 로그인 → JWT(access+refresh) 발급 → 웹 챗봇 UI 이용 가능
6. 거부 시: 사용자에게 거부 사실을 안내(웹페이지 등)하고 자격증명(사내 계정 PW, 앱 로그인 비밀번호 모두)은 폐기

### 해피 패스 (예약 요청) — 계정 등록 완료 후

1. 사용자가 챗봇에 목적, 날짜, 시간대(+선호 인원수 등)를 입력
2. Agent가 사내 예약 시스템에서 해당 조건의 가용 회의실/시간을 조회하되, **먼저 그 사용자의 "선호 회의실 목록"을 우선순위 순서대로 확인** — 비어있는 곳이 있으면 그것부터 제안, 선호 회의실이 전부 예약되어 있으면 **우선순위 낮은/선호 목록 밖의 예약 가능한 회의실들을 바로 리스트업해서 함께 제시**
3. Agent가 가능한 옵션을 사용자에게 안내
4. 사용자가 옵션 중 하나를 선택(또는 확정 요청)
5. Agent가 사내 예약 시스템에 예약을 생성 → 자동 확정
6. Agent가 예약 결과(회의실, 시간, 확정 여부)를 챗봇으로 피드백

### 조건(인원수 등) 검색

1. 사용자가 "8명 이상 가능한 회의실 있어?"처럼 시간대 + 인원수 조건을 함께 물음
2. Agent가 가용성 조회 결과에 회의실별 수용인원(`room_info.ATTENDER_LIMIT`, 9번 참고)을 결합해 조건을 만족하는 회의실만 필터링
3. 조건에 맞는 회의실 목록을 안내 (선호 회의실이 조건도 만족하면 그것을 우선 제시)

### 이력 기반 추천 ("자주 쓰던 회의실")

1. 사용자가 "자주 쓰던 회의실로 예약해줘"처럼 이력 기반 표현을 사용
2. 가입 시 등록한 "선호 회의실"이 있으면 그것을 그대로 1순위로 사용
3. 등록된 선호 회의실이 없으면, 취소되지 않은 과거 예약을 회의실별로 집계해 **예약 횟수가 가장 많은 회의실**을 후보로 제시 (`get_user_frequent_rooms`, 6번 참고)

### 긴 회의 요청 (2시간 초과 → 회의실 분할 예약)

"동일 사용자+동일 회의실" 하루 합계 2시간 제한(6번 참고) 때문에, 한 회의실에서 2시간 넘게 연속으로 예약할 수 없다. 3시간처럼 2시간을 넘는 연속 시간대를 요청하면 **서로 다른 회의실 여러 개로 나눠서, 시간이 이어지도록 예약**하는 방식으로만 가능하다.

1. 요청한 시간대 길이가 120분을 초과하면 분할 대상으로 판단
2. 필요한 회의실 개수 계산: 세그먼트 수 = ceil(요청 분 / 120), 30분 단위를 유지하며 **앞쪽 세그먼트부터 최대 120분씩 채우고 남는 시간을 마지막 세그먼트에 배정** (예: 3시간=180분 → 120분+60분, 5시간=300분 → 120분+120분+60분)
3. 각 세그먼트마다 별도로 가용 회의실을 탐색 — **선호 회의실 우선순위**는 그대로 적용하되, 같은 회의실이 두 세그먼트에 배정되지 않도록 하고(이미 그날 그 사용자가 일부 사용한 회의실이면 남은 한도만큼만 후보로 고려), 이동 편의를 위해 가능하면 같은 층/인접 층을 우선한다
4. 확정 전, 전체 계획("14F-2 14:00~15:30 + 14F-3 15:30~17:00, 총 2개 회의실")을 사용자에게 보여주고 **한 번에 확인**받는다 (세그먼트마다 따로 묻지 않음)
5. 확인되면 세그먼트별로 `checkRoom → checkStraightRoom → checkDayCountLimit → SaveReserve`를 순차 실행해 각각 별도의 확정 예약(Reservation)을 생성한다
6. **부분 실패 처리**: 중간에 한 세그먼트가 실패하면(예: 그 사이 다른 사람이 선점), 이미 생성된 이전 세그먼트 예약을 `delReserve`로 자동 취소하고(보상 트랜잭션), 사용자에게 실패 사실과 함께 재조회를 제안한다 — 예약 시스템에 여러 건을 묶는 진짜 트랜잭션이 없으므로 애플리케이션 레벨에서 전부 성공 또는 전부 취소를 보장한다
7. DB 저장: 분할된 예약들은 각각 별도의 `reservations` row가 되지만, 모두 같은 `reservation_requests.id`를 `reservation_request_id`로 참조하므로 **스키마 변경 없이 1건의 요청 ↔ N건의 확정 예약**을 그대로 표현할 수 있다 (역방향 FK 활용)

### 내 예약 조회

1. 사용자가 "오늘/내일/이번 주 내 예약 뭐 있어?" 같은 질문을 함
2. Agent가 우리 DB(`reservations`)에서 이 챗봇으로 만든 예약을 조회하고, `bindMyReservation`(9번 API 참고)으로 해당 기간의 **CJ 실제 예약 목록**도 함께 조회
3. 목록을 정리해서 답변 (없으면 "예약 내역 없음"으로 응답). **같은 `reservation_request_id`를 공유하는 예약이 여러 건이면(위 "긴 회의 요청" 분할 케이스) 하나로 묶어서 "OO~OO 연속 회의 (2개 회의실로 분할: 14F-2, 14F-3)"처럼 안내한다** — 사용자에게는 서로 다른 두 건의 예약이 아니라 하나의 회의로 인식되게 함
4. **[2026-08-31 추가, 실사용에서 발견]** 이 챗봇을 거치지 않고(CJ WORLD 웹사이트에서 직접 등) 잡은 예약은 우리 DB에 없어서, DB만 보던 이전 버전은 이런 예약을 "없다"고 잘못 안내했다. 이제 `bindMyReservation`의 실제 응답을 `cj_seq`로 우리 DB 기록과 교차 대조해서, DB에 없는 CJ 예약도 "이 챗봇 밖에서 잡힌 예약"으로 구분해 함께 보여준다 — 단, 그런 예약은 우리 DB에 행이 없어 **이 챗봇으로는 변경/취소할 수 없다**는 점을 사용자에게 알린다.

### 예약 변경

지금까지의 시나리오는 "선호 회의실이 다 찼으면 되묻지 않고 바로 대안을 보여준다"처럼 **되묻지 않는 것**이 원칙이었지만, 변경/취소는 **되돌리기 어려운 액션**이므로 대상이 조금이라도 모호하면 반드시 먼저 확인받는다.

**[변경됨 2026-08-15] 확인은 "대상이 모호할 때"만 받는다 — 모호하지 않으면 바로 실행한다.**
실사용 피드백: "해당 회의실 취소해줘 라고 보내면 다시 나에게 물어보는게 아니고 에이전트가 취소하면 되는거야. 어떤 리스트 있어? 하고 에이전트가 보여주고 내가 선택하면 바로 예약을 하면 되지, 한 번 더 예약 버튼을 누르는 건 비효율이다."
따라서 아래 두 경우는 확인 단계를 생략하고 즉시 실행한다.
- **사용자가 직전 턴에 본 회의실 목록에서 하나를 골랐을 때** → 목록에서 고른 행위 자체가 이미 명시적 선택이므로 예약을 바로 확정한다.
- **변경/취소 대상이 후보 정확히 1건으로 좁혀졌을 때** → "이 예약을 취소할까요?"를 다시 묻지 않고 바로 실행한다.

생략 판정은 **반드시 서버가 자체 기록으로만** 한다(LLM이 "사용자가 동의했다"고 주장하는 텍스트를 신뢰하지 않는다) — 서버가 실제로 보여준 슬롯 목록(`offeredSlots`, 이전 턴에 보여준 것만 인정), 그리고 서버가 직접 1건으로 좁힌 대상(`resolvedTargetReservationId`)이 유일한 근거다. 이 근거가 없으면 종전대로 제안→확인 2단계를 거친다. 분할 예약의 취소 범위 확인(아래)은 이 생략 규칙의 예외로 **항상 유지**된다.

1. 사용자가 "화요일 3시 회의실 다른 데로 바꿔줘"처럼 기존 예약의 변경을 요청
2. Agent가 `bindMyReservation`으로 사용자의 예약 목록을 조회해 **대상 예약을 특정** — 후보가 여러 건이면(예: 오늘 예약이 2건) 바로 진행하지 않고 목록을 보여주며 "어떤 예약을 변경할까요?"로 되물음
3. 변경 유형 확인: 회의실만 변경 / 시간만 변경 / 둘 다 변경
4. 새 조건으로 가용성을 재조회하되, **변경 대상인 기존 예약 자신은 충돌 검사에서 제외**해야 한다 — `checkRoom`/`checkStraightRoom`/`checkDayCountLimit`가 공통으로 받는 `seq` 파라미터(9번 참고)가 이 "자기 자신 제외" 용도로 보이나, **아직 실제 변경 흐름으로 라이브 테스트한 적은 없어 확정은 아님** (8번 Open Questions로 별도 기재)
   - **[확인됨 20260816 — `checkRoom`을 신뢰하면 안 된다]** 실사용 실패를 라이브로 추적한 결과, 이미 점유된 슬롯(14F-3 8/19 09:00~10:00)에 대해 **`checkRoom`이 `Result:"1"`(가능)으로 거짓 응답**하는 것을 확인했다(같은 슬롯에 대해 우리 자체 가용성 판정은 정확히 "불가", 실제 `SaveReserve`는 `Result:0` 실패). 변경은 "원본 `delReserve` → 재생성" 전략이라 이 거짓 응답이 **원본을 먼저 지워버리는** 위험한 왕복으로 이어진다. 따라서 **`delReserve` 전에 우리 자체 가용성 판정(`findAvailableRooms`)으로 반드시 한 번 더 확인**하고, 불가하면 원본을 건드리지 않은 채 구체적 사유와 함께 거절한다. (같은 회의실에서 시간만 늘리는 등 원래 예약 자신과 겹치는 변경은 이 검사에서 제외한다.)
5. 변경 후보를 사용자에게 보여주고 확정 전 확인받음 — 단 대상이 이미 1건으로 확정됐으면 위 [변경됨 2026-08-15]대로 바로 실행
6. 확인되면 변경을 실행 — `SaveReserve`가 `reservetype` 값에 따라 수정 모드도 지원하는지, 아니면 `delReserve`(취소) 후 `SaveReserve`(재생성)로 처리해야 하는지는 **미확인** (8번 참고). 후자로 처리할 경우, 재생성이 실패하면 원래 예약이 사라진 채로 남는 위험이 있으므로 재생성 실패 시 원래 예약 정보로 재시도하는 보상 로직이 필요
7. 결과 피드백 (변경 완료 또는 실패 시 원래 예약 유지 여부 안내)
8. **분할 예약(긴 회의) 건의 변경**: "그 3시간짜리 회의 시간 바꿔줘"처럼 대상이 분할 예약이면, 연결된 모든 세그먼트(같은 `reservation_request_id`)를 함께 다룬다는 점을 사용자에게 알리고 진행

### 예약 취소

1. 사용자가 "오늘 3시 회의실 취소해줘"처럼 기존 예약의 취소를 요청
2. Agent가 `bindMyReservation`으로 대상 예약을 특정 — 역시 후보가 여러 건이면 목록을 보여주고 확인받음
3. **분할 예약(긴 회의) 건이면**: 연결된 세그먼트가 여러 개라는 것을 안내하고, "전체 취소"인지 "그중 한 회의실만 취소"인지 확인받음 (기본값을 임의로 정하지 않음 — 취소는 특히 되돌릴 수 없으므로)
4. 대상이 여러 건이라 사용자에게 되물어 좁혀야 했던 경우에만 "OO 회의실 15:00~16:00 예약을 취소할까요?"로 확인 — **대상이 처음부터 1건으로 특정되면 확인 없이 바로 취소**한다(위 [변경됨 2026-08-15])
5. 확인되면 `delReserve(seq)` 호출, DB의 `reservations.status`를 `cancelled`로 갱신
6. 결과 피드백 (취소 완료 안내)

### 반복 예약 규칙 등록 및 자동 실행 — **[신규]**

사내 예약 시스템은 **오늘부터 7일 뒤까지만** 예약을 받기 때문에, "3개월 동안 매주 화요일" 같은 먼 미래의 반복 예약을 미리 한 번에 생성할 수 없다. 대신 우리는 **예약 창이 열리는 그 순간 자동으로 잡는 스케줄러**를 제공한다.

#### 규칙 등록 (사용자의 일회성 작업)

1. 사용자가 앱 사이드바(모바일은 "내 정보" 시트)의 "반복 예약" 폼에 들어감
2. 다음을 입력:
   - **요일**: 매주 어느 요일인가 (0=일요일 ~ 6=토요일, JS Date.getDay() 규약)
   - **시간**: 시작·종료 시각 (예: 10:00~12:00, 30분 단위)
   - **회의명/내용**: 회의 제목과 설명
   - **회의실 우선순위**: 1순위, 2순위, 3순위로 고르고 싶은 회의실 (1~3개, 우선순위 순서로 시도)
3. 저장 전에 **무인 예약 동의**를 받는다:
   - 동의 없이는 규칙 생성 불가
   - 동의는 3중 게이트: ① 규칙 생성 시 ② 매 자동 실행 전 재확인 ③ 철회 시 모든 규칙 즉시 비활성화
4. 저장 완료 — 이후 대상일이 되면 자동으로 실행됨

#### 자동 실행 (Windows 작업 스케줄러, 사무실 PC)

1. **대상일 7일 전 00:01에** Windows 작업 스케줄러(사무실 PC)가 자동 실행
2. 사용자의 등록된 규칙을 읽음
3. **1순위 회의실부터 차례로 시도**:
   - 대상일이 예약 윈도우 범위 내인지 확인 (오늘~7일)
   - 1순위가 비어있으면 예약
   - 1순위가 다 찼으면 2순위 시도, 2순위도 다 찼으면 3순위 시도
   - 모두 실패하면 실패 기록 저장
4. 실행 결과를 **앱 안에만 로그**로 표시 (사이드바 "반복 예약 실행 이력")
   - 성공: "OO 날짜 OO 회의실 예약됨"
   - 실패: "OO 날짜 예약 실패 (1순위: 만석, 2순위: 만석, 3순위: 만석)"

#### 제약과 한계

- **[미검증]** 이 시스템의 +7일 예약 창이 정확히 자정에 열린다는 것은 확인되지 않았다 — 실사용에서 시간이 맞지 않으면 재조정 필요
- **[기술적 한계]** 스케줄러를 실행하는 Windows PC가 켜져 있고 사내망에 연결되어 있어야만 실행된다 — PC가 꺼져있거나 절전 상태면 그날 예약은 실패한다
- **[권한 확대 전제]** 사용자가 앱에 없을 때 서버가 사용자의 사내 계정으로 무인 로그인하여 예약한다 — 이는 기존의 "사용자 요청 시에만 복호화" 대비 권한이 확대되므로 명시적 동의를 받는다

### 비밀번호 변경 / 사내 계정 PW 재등록 — **[추가됨 20260816]**

사내 계정 PW는 사내 정책상 주기적으로 만료된다. 사용자가 여기서 비밀번호를 바꾸면 우리가 보관한 암호문이 낡은 값이 되어 로그인이 전부 실패하고 **그 사용자에게는 앱 전체가 멈춘다.** `email_alias`가 unique라 재가입도 막히므로, 재등록 수단이 없으면 시간이 지날수록 사용자가 하나씩 잠기게 된다. 따라서 이건 편의 기능이 아니라 **필수 복구 경로**다.

1. **저장 전 검증**: 새 사내 계정 PW로 **실제 로그인을 시도**해 맞는지 확인한다. 검증에 성공한 값만 저장한다 — 검증 없이 저장하면 오타 하나로 이후 모든 동작이 죽는데 사용자는 원인도 모르고 되돌릴 수도 없다.
2. 저장 후 옛 비밀번호로 맺어둔 **세션 캐시를 즉시 버린다.**
3. 진입 경로는 사용자의 상태에 따라 둘로 나뉜다.
   - **아직 로그인이 되는 상태** — 챗봇 화면 사이드바(모바일은 "내 정보" 시트)에서 재등록
   - **이미 로그인이 막힌 상태** — 로그인 시점에 세션 확보를 강제하므로(위 온보딩 5번 + 6번 "[결정됨]" 참고) 앱에 들어올 수 없다. 그래서 **로그인 화면에서 바로 재등록**할 수 있어야 하며, 이때 본인 확인은 JWT가 아니라 **앱 로그인 비밀번호**로 한다.
4. **앱 로그인 비밀번호 변경**도 같은 자리에서 가능하다. 현재 비밀번호를 확인한 뒤 교체하고, 성공하면 그 사용자의 Refresh Token을 전부 폐기해 다른 기기의 로그인 상태를 끊는다.
5. **[미결]** 비밀번호를 **잊어버린** 경우의 자가 재설정은 아직 지원하지 않는다 — 메일 발송 수단이 없어서 본인 확인을 할 방법이 없다. 현재는 Admin 대행만 가능하다.

### 예외/분기 상황

- **요청 시간대 충돌**: 요청한 시간대에 예약 가능한 회의실이 없는 경우 → Agent가 대체 가능한 시간대 또는 다른 회의실을 추천
- **사내 계정 PW 만료/변경으로 인증 실패**: 저장된 자격증명으로 로그인이 안 되는 경우 → 예약 진행 불가, **"사내 계정 PW를 바꾸셨다면 앱에도 다시 등록해야 한다"고 안내하고 재등록 경로를 제공**한다 (위 "비밀번호 변경" 프로세스)
- **인증 실패**: 사내 계정 시스템 계정 연동이 안 된 사용자가 요청 → 예약 진행 불가, 안내 메시지 반환
- **미등록/승인 대기 중 사용자가 챗봇 사용 시도**: 온보딩을 마치지 않았거나 Admin 승인 대기 중인 사용자가 예약을 요청 → 예약 진행 불가, 등록 웹페이지 링크 또는 승인 대기 상태 안내
- **외부 시스템 연동 실패**: 사내 예약 시스템 API/세션이 응답하지 않는 경우 → 재시도 또는 실패 안내 (※ 세부 정책은 확인 필요, 8번 참고)
- **범위 밖 요청**: 존재하지 않는 층(예: "10층"), 지원 안 하는 사업장(상암S시티·YTN 본사 외), 장비 조건 검색, 챗봇에서 반복 예약 규칙을 생성하려는 요청 등을 요청 → 예약을 시도하지 않고 "그건 아직 지원하지 않는다"고 명확히 안내 (반복 예약은 챗봇이 아니라 사이드바 폼에서만 등록 가능, 아래 "요청 처리 가능 여부 판단" 원칙 참고)

## 3. 도메인 용어 (Ubiquitous Language)

| 용어                              | 의미                                                       | 비고                          |
| --------------------------------- | ---------------------------------------------------------- | ----------------------------- |
| 예약 요청(Reservation Request)    | 사용자가 챗봇에 입력한 목적/날짜/시간대 조건               | 확정 전 상태                  |
| 예약(Reservation)                 | 특정 회의실 + 특정 시간대가 특정 사용자에게 확정 배정된 것 | 자동 확정, 승인 절차 없음     |
| 가용성 조회(Availability Check)   | 요청 조건에 맞는 회의실/시간대가 비어있는지 확인하는 동작  | 사내 예약 시스템 조회 필요    |
| 대체 추천(Alternative Suggestion) | 요청 조건이 불가할 때 Agent가 제시하는 다른 시간/회의실    | 충돌 시에만 발생              |
| 사내 계정 시스템 계정(Corporate Account)  | 자동화(예약 실행)에 쓰이는 사내 인증 정보. 이 서비스 자체 로그인(웹 회원가입/JWT)과는 별개 | 회원가입 시 앱 로그인 계정과 함께 등록, 텔레그램 채널 추가 시 텔레그램 계정과도 매핑 예정 |
| 사내 계정 시스템 ID / 사내 계정 PW         | 위 계정의 아이디와 비밀번호. **사용자에게 보이는 모든 화면·메시지에서 이 명칭만 쓴다** | **[변경됨 20260816]** 이전 표기 "사내 계정 ID/비밀번호"는 앱 로그인 비밀번호와 헷갈린다는 실사용 피드백으로 폐기. DB 컬럼명(`email_alias`, `encrypted_password`)은 그대로 |

## 4. 핵심 엔티티

### User (요청자)

- 설명: 챗봇으로 예약을 요청하는 사내 직원. 온보딩 프로세스(회원가입 신청 → Admin 승인 → 로그인)를 마쳐야 이용 가능
- 주요 속성: 사용자ID, 사내 계정 시스템 ID(email_alias), 암호화된 사내 계정 PW(참조, 자동화 로그인용, 복호화 가능), **앱 로그인 비밀번호 해시(단방향, 이 서비스 자체 로그인용)**, **텔레그램 사용자ID(딥링크로 확보, 위조 불가 — 텔레그램 채널 추가 시 사용, 현재는 미사용)**, 등록 승인 일시, 동의 철회 여부, **선호 회의실 목록(우선순위 순서, 가입 시 입력)**, **무인 예약 동의(사용자 없이 서버가 반복 예약 규칙을 자동 실행하는 것에 대한 동의 여부 및 시각, 철회 시각)**
- 상태(life-cycle): 등록 신청됨(대기) → 승인됨(이용 가능) / 거부됨 → 동의 철회(삭제 요청)

### AccountRegistrationRequest (계정 등록 요청)

- 설명: 사용자가 등록 웹페이지에서 제출한 사내 계정 시스템 계정 등록/텔레그램 연동 신청 건. 화이트리스트 미해당 시 Admin의 승인 대상
- 주요 속성: 신청ID, 사내 계정 시스템 ID, 암호화된 사내 계정 PW, **앱 로그인 비밀번호 해시**, (텔레그램 채널 추가 시) 텔레그램 딥링크 토큰·연동된 텔레그램 사용자ID, 상태(대기/자동승인/승인/거부), 처리한 Admin(자동승인 시 "system"), 처리 일시
- 상태(life-cycle): 대기(Pending) → 승인(Approved, 수동 또는 자동) / 거부(Rejected)

### AdminWhitelist (Admin 화이트리스트)

- 설명: 가입 즉시 자동으로 Admin 권한을 받는 사내 계정 시스템 ID 목록. 별도 승인 절차 없이 Admin 부트스트랩 문제를 해결하기 위한 사전 등록 목록
- 주요 속성: 사내 계정 시스템 ID, 등록 사유/등록자, 등록 일시
- 상태(life-cycle): 없음(정적 목록, Admin만 추가/제거 가능)

### Room (회의실) — 개별 예약 단위. 건물/층이 아니라 "회의실 그 자체"를 가리킴

- 설명: 예약 대상이 되는 사내 회의실. 실제 시스템은 **사업장(Site) → 층(Floor) → 회의실(Room)** 3단계 계층으로 관리되며, `Room`은 그중 가장 하위, 실제로 예약되는 최소 단위임
  - 사업장(Site) 예: 상암S시티 (`area_code`=804), YTN 본사 (`area_code`=997) — **[변경됨 20260826]** 지원 사업장은 이 두 곳(6번 참고). CJ 시스템에는 이 외에도 충청지사(대전)/창원지사/아산지사/부산지사/대구지사/공유오피스 등이 더 있으나(`listArea` type=0으로 조회됨) 이 프로젝트 범위 밖이라 대상에서 제외한다.
  - 층(Floor) 예: 상암S시티 3F(`sub_area_code`=1128)·12F(1111)·13F(805)·14F(807)·15F(808)·16F(806), YTN 본사 17F(1002) — YTN 본사는 CJ 시스템상 17F 단 하나뿐임을 `listArea`(type=1, areacode=997)로 실측 확인함(2026-08-26)
  - **회의실(Room) 예: 3F-1, 12F-3 (`room_code`, 예: 4539), YTN 본사 대회의실(`room_code`=3945)** ← 이 엔티티가 가리키는 대상
- 주요 속성: 회의실명(예: "3F-1"), 소속 층(Floor), 소속 사업장(Site, 상암S시티 또는 YTN 본사), 수용인원 (※ 장비/용도 속성은 1차 범위 제외 — 기본 정보만)
- 상태(life-cycle): 사용 가능 / 사용 중(예약됨)

### Reservation (예약)

- 설명: 특정 Room + 시간대 + User로 구성된 확정 예약 건
- 주요 속성: 예약ID, Room, 요청자(User), 시작/종료 시간, 목적, 상태(확정/취소됨/변경됨)
- 상태(life-cycle): 확정(Confirmed) → 변경됨(Modified) / 취소됨(Cancelled)

### ReservationRequest (예약 요청)

- 설명: 사용자가 챗봇에 입력한 원본 조건(가용성 조회 및 예약 생성의 입력값)
- 주요 속성: 목적, 희망 날짜, 희망 시간대, 요청자
- 상태(life-cycle): 접수 → 가용성 확인 → 확정/충돌

### AlternativeSuggestion (대체 추천)

- 설명: 요청 시간대가 충돌할 때 Agent가 제시하는 대안 목록
- 주요 속성: 추천 Room, 추천 시간대, 원본 요청과의 유사도(우선순위)
- 상태(life-cycle): 제시됨 → 선택됨/미선택

## 5. 엔티티 간 관계

- 한 User는 정확히 하나의 승인된 AccountRegistrationRequest로부터 생성된다 (User는 등록 승인의 결과물).
- AccountRegistrationRequest의 신청 ID가 AdminWhitelist에 존재하면 자동 승인되고, 그렇지 않으면 기존 Admin(User 중 Admin 권한 보유자)의 수동 승인이 필요하다.
- 한 User는 여러 ReservationRequest를 만들 수 있다.
- 한 ReservationRequest는 성공 시 하나의 Reservation으로 이어지거나, 충돌 시 여러 AlternativeSuggestion을 가질 수 있다.
- 한 Room은 여러 Reservation을 가질 수 있으나, 동일 시간대에는 하나의 Reservation만 가능하다(겹침 불가).
- 한 Reservation은 하나의 Room, 하나의 User에 귀속된다.

## 6. 비즈니스 규칙 / 제약조건

- **[결정됨] 요청 처리 가능 여부 판단 (일반 원칙)**: Agent는 어떤 요청이 와도, 도구를 호출하기 전에 먼저 "이게 우리가 정의한 능력과 범위 안의 요청인가"부터 판단한다.
  - 판단 기준 ①: 요청이 정의된 도구(가용성 조회/예약 생성/변경/취소/내 예약 조회 등) 중 하나로 매핑되는가
  - 판단 기준 ②: 알려진 제약 — 상암S시티·YTN 본사 두 사업장만 지원(상암S시티 3F·12~16F, YTN 본사 17F), 운영시간 07:00~19:00, 동일회의실 하루 2시간 제한, 예약은 오늘~7일 뒤까지만, 챗봇에서는 반복 예약 규칙 생성 미지원(사이드바 폼에서만), 장비조건 검색 미지원 — 을 벗어나지 않는가
  - 둘 중 하나라도 아니면 **억지로 시도하거나 결과를 지어내지 않는다**. 범위를 벗어난 게 명확하면 "그건 아직 지원하지 않는다"고 바로 안내하고, 지원 여부가 애매하면(목록에 없는 새로운 표현 등) 추측하지 않고 사용자에게 되물어 확인한다.
  - 이 원칙은 지금까지 정리된 개별 시나리오 목록에 없는, **앞으로 나올 새로운 요청**에도 동일하게 적용되는 상위 원칙이다.
- 예약은 승인 절차 없이 **자동 확정**된다.
- 동일 회의실·동일 시간대에 예약이 이미 존재하면 신규 예약 불가 → 이 경우 **대체 가능한 시간/회의실을 추천**해야 한다.

- 사내 계정 시스템 계정과 연동되지 않은 사용자는 예약을 진행할 수 없다.

- **[확인됨]** 1회 최대 예약 시간: 2시간

- **[결정됨]** 사용자 등록은 **웹페이지 신청 → Admin 승인** 절차를 거쳐야 하며, 승인 전에는 챗봇을 통한 예약 요청이 불가하다.
- **[결정됨]** 신청 ID가 **Admin 화이트리스트**에 있으면 승인 절차 없이 즉시 자동 승인 + Admin 권한 부여. 그 외에는 등록된 Admin 전원에게 알림 메일 발송 → Admin이 웹 패널에서 수동 승인.
- **[결정됨]** 승인 알림 메일에는 비밀번호(또는 그와 관련된 어떤 정보도) 포함하지 않으며, 메일의 링크는 인증된 Admin 웹 패널로만 연결한다 (메일 링크 클릭만으로 승인되지 않음).
- **[보류 — 텔레그램 채널 추가 시 재적용]** 텔레그램 사용자 신원 확인은 사용자가 채팅으로 자기신고(自己申告)한 값(예: "제 ID는 OOO입니다")을 신뢰하지 않는다. **등록 시점에 텔레그램 딥링크(`t.me/봇?start=토큰`)로 확보한, 위조 불가능한 텔레그램 사용자ID만을 신원 확인 근거로 사용**한다. (지금은 웹 채널이 1차이므로 아래 웹 로그인 규칙이 우선 적용된다.)
- **[결정됨]** 웹 채널의 신원 확인은 **자체 회원가입/로그인(JWT)** 으로 한다. 회원가입 시 사내 계정 비밀번호(암호화 저장, 자동화용)와 앱 로그인 비밀번호(해시 저장, 로그인 검증용)를 분리해서 저장하며, 둘을 혼용하지 않는다. 로그인은 Admin 승인이 완료된 사용자만 가능하다. 상세는 `docs/4-prd.md` "인증/보안" 참고.

## 7. 바운디드 컨텍스트 (하위 도메인 구분)

- **예약 도메인 컨텍스트**: 가용성 조회, 예약 생성/변경/취소, 충돌 판정 및 대체 추천 로직
- **외부 연동 컨텍스트**: 사내 예약 시스템(API 또는 세션/쿠키 기반)과의 통신 — 이 서비스 자체 로그인과는 별개

- **계정 등록/관리 컨텍스트**: 회원가입 웹페이지, 로그인 페이지, Admin 승인/거부 처리 — 챗봇 인터페이스 컨텍스트와는 별도의 웹 화면(Admin용) 필요. 텔레그램 딥링크 연동은 텔레그램 채널 추가 시 이 컨텍스트에 다시 포함

## 9. 외부 연동 API 명세 (확인됨)

Playwright로 실제 사이트에 로그인하여 조회→예약→취소 전체 흐름을 실행하며 확인한 내용. 모두 사내 SSO 로그인 세션 쿠키가 있어야 호출 가능 (공식 API 문서 없음, ASP.NET ASMX 웹서비스).

### 로그인/세션 확보 흐름 [2026-08-13 재검증, 이후 BE-7 라이브 테스트 중 한 번 더 재검증 — 이전 버전(Azure AD 가정, 이후 iframe 직접 URL 가정)을 대체함]

- **로그인은 `예약 서버`이 아니라 `로그인 포털`(사내 포털)에서 한다.** `예약 서버`에 직접 접근하면 사내망 범용 404로 리다이렉트되고 로그인 폼 자체가 없다.
- 로그인 폼은 **Azure AD/Microsoft 표준 폼이 아니라 로그인 포털 자체 로그인 폼**이다(`/PT/login.aspx`). 실측 셀렉터: 아이디 `input#txtID`, 비밀번호 `input#txtPWD`, 로그인 버튼은 `<a class="btn_login" onclick="Login()">` (submit 버튼이 아니라 JS `Login()`을 호출하는 링크 — 비밀번호를 클라이언트에서 인코딩(`EnCode()`)한 뒤 폼을 제출하므로 반드시 Playwright로 실제 클릭을 재현해야 함).
- 로그인 실패 시 URL이 `/PT/login.aspx`에 그대로 머물고 `#divErrorLogin` 요소가 노출되며 "아이디 또는 비밀번호 오류입니다..." 메시지가 뜬다.
- 로그인 성공 시 URL은 바로 바뀌지 않고, 내부적으로 로그인 포털의 포털 메인 대시보드 `/NPT/PortalBuilder/23_main.aspx`로 이동한다. `.cj.net`(상위 도메인 공유) 쿠키(`cAccess_token`, `ck`, `CJW`, `N_CJW`, `m365_id` 등)가 이때 발급된다.
- **[2026-08-13 재정정] `로그인 포털`과 `예약 서버`의 세션 공유는 URL 직접 이동으로 되지 않는다.** 로그인 포털의 `/NPT/PortalBuilder/23_service.aspx?CONTENTS_ID=EPCT3427`는 실서버 페이지가 아니라, 포털 메인(`23_main.aspx`) 안의 JS 함수 `select_menu('EPCT3427','LSB')`가 클라이언트 사이드로 콘텐츠를 스왑하는 방식이다 — 이 URL로 직접 `page.goto`하면 `net::ERR_ABORTED`로 실패한다. **반드시 `23_main.aspx`를 먼저 로드한 뒤, 그 안의 회의실예약 버튼(`button#bntConf`, `onclick="select_menu('EPCT3427','LSB')"`)을 실제로 클릭해야 한다.** 이 클릭이 `예약 서버`으로의 SSO 핸드셰이크(`/NConf/Anonymity/nconfFilter.aspx` 리다이렉트, `.cj.net` 쿠키 근거)를 트리거하고, `예약 서버` 도메인 전용 쿠키 `AP`를 클릭 후 1초 내에 발급한다(실측 확인). **`로그인 포털` 로그인만으로는 부족하고, 반드시 이 버튼을 눌러야 `예약 서버` API 호출이 가능한 세션이 만들어진다.**
- 이렇게 얻은 쿠키(`예약 서버` 도메인 쿠키 + `.cj.net` 공유 쿠키)만 있으면 **브라우저 없이 순수 HTTP 요청으로 ASMX API를 정상 호출할 수 있음을 실측 확인**했다 — "로그인은 Playwright, API 호출은 가벼운 HTTP 클라이언트" 전략이 그대로 유효하다. `X-Requested-With`/`Referer` 헤더는 없어도 정상 동작한다(실측 확인, 있어도 무방).

**주의할 점**

- 회의실 위치 식별자가 두 계층으로 쓰이는데 이름이 혼용됨: 건물(`area_code`, 예: 804) / 층(`sub_area_code` 또는 `subarea_code`, 예: 1128) / 회의실(`room_code`). 검증용 API들(`checkRoom` 등)은 층 코드를 `area_code`라는 이름으로 받으므로 구현 시 혼동 주의.
- **[정정 — 이전 결론을 뒤집음]** 조회 응답 인코딩은 **실제로는 항상 UTF-8이다.** 이전 버전은 브라우저(Playwright `response.text()`)로 관찰했을 때 `Content-Type`에 charset이 없는 응답에서 한글이 깨지는 것을 보고 "UTF-8이 아니다"로 결론 내렸으나, 이는 브라우저 쪽 디코딩 방식의 artifact였다. Node.js에서 raw bytes(`response.arrayBuffer()`)를 직접 UTF-8로 디코딩하면 한글이 정상적으로 나옴을 실측 확인했다(예: "하위", "8인" 등). **`Content-Type` 헤더를 신뢰하지 말고 항상 UTF-8로 디코딩할 것** — EUC-KR 디코딩을 시도하면 오히려 깨진다.
- 저장 전 `checkRoom` → `checkStraightRoom` → `checkDayCountLimit` 3개 검증을 순서대로 통과해야 `SaveReserve` 호출이 의미 있음 (프론트 로직을 그대로 따라야 함).
- 이 API들은 공식 문서화된 것이 아니라 **실제 브라우저 동작을 관찰하여 역으로 확인한 것**이므로, 사내 IT/인프라팀에 정식 연동 승인 여부를 반드시 확인해야 한다 (8번 Open Questions 참고).
- **[확인됨]** `getDayPilotConfReserveList` 응답의 `reserve_all_list`는 회의실별 30분 단위 문자열이며, **`Y`=이미 예약됨(불가) / `N`=예약 가능(빈 시간)** 이다 (실제 예약 생성 결과로 교차 검증 완료).
- **[신규 발견 — 2026-08-13, BE-7 라이브 검증 중]** `reserve_all_list`의 실제 바이트 형태는 회의실별 문자열들의 배열이 아니라, **`"룸코드:슬롯문자열|룸코드:슬롯문자열|..."` 형태로 전체 층의 모든 회의실을 파이프(`|`)로 이어붙인 단일 문자열**이다(예: `"4502:NNNYYYYYYYNNYYYYYYYYNNNNNN|4503:NNNNYYYYYYNNNNYYYYYYNNNNNN|"`). 이걸 JSON 배열로 잘못 가정하면 항상 빈 배열로 파싱되어 **모든 회의실이 상시 "불가"로 오판되는 치명적 버그**가 된다 — 실제로 BE-4/BE-6 구현 당시 fixture(서술을 재구성한 것, 실측 원본 아님)로는 이 문제가 드러나지 않다가 BE-7 라이브 테스트에서 발견/수정됨(`backend/src/tools/availability.tool.ts`의 `parseReserveAllList`). 또한 `event_list`의 `start`/`end`는 `"HH:mm"`이 아니라 전체 ISO 타임스탬프(`"2026-08-13T08:30:00"`)이므로 시간 비교 전에 `HH:mm`으로 변환해야 한다(`isoTimestampToHHmm`).
