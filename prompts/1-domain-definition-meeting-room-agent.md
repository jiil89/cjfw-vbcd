# 도메인 정의서 — 회의실 예약 Agent

## 0. 문제 상황 (왜 이 서비스가 필요한가)

- 업무 특성상 **미팅을 매우 자주** 해야 한다.
- 인원수/시간대에 맞는 회의실을 **빠르게** 잡아야 할 때가 많은데, 지금은 예약 화면을 직접 열어서 **언제 어디가 비어있는지 하나하나 눈으로 확인**하고, **직접 타이핑해서 저장**해야 한다 — 이 과정 자체가 번거롭고 느리다.
- 이 지연이 실제로 **관련 업무를 하루이틀 늦추는 경우**도 있다 — 단순 불편이 아니라 실제 업무 손실로 이어짐.
- 그래서 필요한 조건(인원수/시간대 등)에 맞는 회의실을 **빠르게 확인하고, 쉽게 예약**할 수 있는 서비스가 필요하다. 이게 이 프로젝트의 존재 이유다.

## 1. 프로젝트 개요

- 서비스 설명: 사용자가 챗봇(1차 채널: 웹 챗봇, 텔레그램/카카오톡은 추후 확장)에 목적·날짜·시간대를 입력하면, Agent가 사내 회의실 예약 현황을 확인해 가능한 회의실/시간을 안내하고, 사용자 요청에 따라 예약을 자동으로 확정한 뒤 결과를 피드백하는 시스템.
- 주요 사용자(액터):
  - 직원(요청자): 챗봇으로 예약을 요청/변경/취소하는 사람
  - Agent(시스템): 가용성 조회, 예약 확정, 충돌 시 대안 추천, 결과 피드백을 수행하는 주체
  - (참고) 회의실 관리자: 이번 범위에서는 승인 절차 없음(자동 확정) → 별도 액터로 개입하지 않음
  - **Admin(서비스 관리자)**: 직원의 사내 계정 등록 요청을 검토·승인/거부하는 사람. 회의실 예약 자체에는 관여하지 않고, **최초 계정 등록 단계에서만** 개입함

## 2. 핵심 업무 프로세스

### 사용자 온보딩(회원가입 → 승인 → 로그인) 프로세스 — 예약 이용 전 최초 1회

**[변경됨]** 1차 채널이 웹 챗봇으로 바뀌면서, 신원 확인 방식도 텔레그램 딥링크에서 **자체 회원가입/로그인(이메일·비밀번호 기반 JWT)** 으로 바뀌었다 (`prompts/prd.txt` "인증/보안" 참고). 텔레그램 딥링크 방식은 텔레그램 채널이 실제로 추가될 때 별도 신원 확인 수단으로 재검토한다.

1. 사용자가 **회원가입 웹페이지**(= 기존 "등록 웹페이지")에 접속해 사내 계정 ID/PW, **선호 회의실(우선순위 순서)**, 그리고 **이 앱 전용 로그인 비밀번호**를 함께 입력해 신청
2. 요청 접수 즉시 두 비밀번호를 각각 다르게 저장한다 — **사내 계정 비밀번호는 복호화 가능한 암호화**(CJ 자동화 로그인에 필요), **앱 로그인 비밀번호는 단방향 해시**(로그인 검증에만 필요, 복호화 불필요). 평문은 어떤 단계에서도 로그/화면/메일에 노출하지 않음
3. **Admin 화이트리스트(사전 등록된 사내 계정 ID 목록) 대조**:
   - 신청한 ID가 화이트리스트에 있으면 → **자동 승인**, 즉시 Admin 권한 부여 + 로그인 가능
   - 화이트리스트에 없으면 → "대기(Pending)" 상태로 접수, 등록된 모든 Admin의 이메일로 **알림 메일**(신청자 정보만 포함, 비밀번호 절대 미포함) 발송 → 메일의 링크는 Admin 웹 패널(로그인 필요)로 연결, 메일 링크 자체로 즉시 승인되지 않음
4. Admin이 웹 패널에 로그인한 상태에서 승인 또는 거부 처리
5. 승인 시: 사용자가 **로그인 페이지**에서 신청 시 설정한 앱 로그인 비밀번호로 로그인 → JWT(access+refresh) 발급 → 웹 챗봇 UI 이용 가능
6. 거부 시: 사용자에게 거부 사실을 안내(웹페이지 등)하고 자격증명(사내 계정 비밀번호, 앱 로그인 비밀번호 모두)은 폐기

### 해피 패스 (예약 요청) — 계정 등록 완료 후

1. 사용자가 챗봇에 목적, 날짜, 시간대(+선호 인원수 등)를 입력
2. Agent가 사내 예약 시스템에서 해당 조건의 가용 회의실/시간을 조회하되, **먼저 그 사용자의 "선호 회의실 목록"을 우선순위 순서대로 확인** — 비어있는 곳이 있으면 그것부터 제안, 선호 회의실이 전부 예약되어 있으면 **우선순위 낮은/선호 목록 밖의 예약 가능한 회의실들을 바로 리스트업해서 함께 제시**
3. Agent가 가능한 옵션을 사용자에게 안내
4. 사용자가 옵션 중 하나를 선택(또는 확정 요청)
5. Agent가 사내 예약 시스템에 예약을 생성 → 자동 확정
6. Agent가 예약 결과(회의실, 시간, 확정 여부)를 챗봇으로 피드백

### 조건(인원수 등) 검색

1. 사용자가 "8명 이상 가능한 회의실 있어?"처럼 시간대 + 인원수 조건을 함께 물음
2. Agent가 가용성 조회 결과에 회의실별 수용인원(`room_info.ATTENDER_LIMIT`, 9번 참고)을 결합해 조건을 만족하는 회의실만 필터링
3. 조건에 맞는 회의실 목록을 안내 (선호 회의실이 조건도 만족하면 그것을 우선 제시)

### 이력 기반 추천 ("자주 쓰던 회의실")

1. 사용자가 "자주 쓰던 회의실로 예약해줘"처럼 이력 기반 표현을 사용
2. 가입 시 등록한 "선호 회의실"이 있으면 그것을 그대로 1순위로 사용
3. 등록된 선호 회의실이 없으면, 취소되지 않은 과거 예약을 회의실별로 집계해 **예약 횟수가 가장 많은 회의실**을 후보로 제시 (`get_user_frequent_rooms`, 6번 참고)

### 긴 회의 요청 (2시간 초과 → 회의실 분할 예약)

"동일 사용자+동일 회의실" 하루 합계 2시간 제한(6번 참고) 때문에, 한 회의실에서 2시간 넘게 연속으로 예약할 수 없다. 3시간처럼 2시간을 넘는 연속 시간대를 요청하면 **서로 다른 회의실 여러 개로 나눠서, 시간이 이어지도록 예약**하는 방식으로만 가능하다.

1. 요청한 시간대 길이가 120분을 초과하면 분할 대상으로 판단
2. 필요한 회의실 개수 계산: 세그먼트 수 = ceil(요청 분 / 120), 각 세그먼트는 30분 단위를 유지하며 가능한 균등하게 분배 (예: 3시간=180분 → 90분+90분, 5시간=300분 → 120분+120분+60분)
3. 각 세그먼트마다 별도로 가용 회의실을 탐색 — **선호 회의실 우선순위**는 그대로 적용하되, 같은 회의실이 두 세그먼트에 배정되지 않도록 하고(이미 그날 그 사용자가 일부 사용한 회의실이면 남은 한도만큼만 후보로 고려), 이동 편의를 위해 가능하면 같은 층/인접 층을 우선한다
4. 확정 전, 전체 계획("14F-2 14:00~15:30 + 14F-3 15:30~17:00, 총 2개 회의실")을 사용자에게 보여주고 **한 번에 확인**받는다 (세그먼트마다 따로 묻지 않음)
5. 확인되면 세그먼트별로 `checkRoom → checkStraightRoom → checkDayCountLimit → SaveReserve`를 순차 실행해 각각 별도의 확정 예약(Reservation)을 생성한다
6. **부분 실패 처리**: 중간에 한 세그먼트가 실패하면(예: 그 사이 다른 사람이 선점), 이미 생성된 이전 세그먼트 예약을 `delReserve`로 자동 취소하고(보상 트랜잭션), 사용자에게 실패 사실과 함께 재조회를 제안한다 — CJ 시스템에 여러 건을 묶는 진짜 트랜잭션이 없으므로 애플리케이션 레벨에서 전부 성공 또는 전부 취소를 보장한다
7. DB 저장: 분할된 예약들은 각각 별도의 `reservations` row가 되지만, 모두 같은 `reservation_requests.id`를 `reservation_request_id`로 참조하므로 **스키마 변경 없이 1건의 요청 ↔ N건의 확정 예약**을 그대로 표현할 수 있다 (역방향 FK 활용)

### 내 예약 조회

1. 사용자가 "오늘/내일/이번 주 내 예약 뭐 있어?" 같은 질문을 함
2. Agent가 `bindMyReservation`(9번 API 참고)으로 해당 기간의 본인 예약 목록을 조회
3. 목록을 정리해서 답변 (없으면 "예약 내역 없음"으로 응답). **같은 `reservation_request_id`를 공유하는 예약이 여러 건이면(위 "긴 회의 요청" 분할 케이스) 하나로 묶어서 "OO~OO 연속 회의 (2개 회의실로 분할: 14F-2, 14F-3)"처럼 안내한다** — 사용자에게는 서로 다른 두 건의 예약이 아니라 하나의 회의로 인식되게 함

### 예약 변경

지금까지의 시나리오는 "선호 회의실이 다 찼으면 되묻지 않고 바로 대안을 보여준다"처럼 **되묻지 않는 것**이 원칙이었지만, 변경/취소는 **되돌리기 어려운 액션**이므로 대상이 조금이라도 모호하면 반드시 먼저 확인받는다.

1. 사용자가 "화요일 3시 회의실 다른 데로 바꿔줘"처럼 기존 예약의 변경을 요청
2. Agent가 `bindMyReservation`으로 사용자의 예약 목록을 조회해 **대상 예약을 특정** — 후보가 여러 건이면(예: 오늘 예약이 2건) 바로 진행하지 않고 목록을 보여주며 "어떤 예약을 변경할까요?"로 되물음
3. 변경 유형 확인: 회의실만 변경 / 시간만 변경 / 둘 다 변경
4. 새 조건으로 가용성을 재조회하되, **변경 대상인 기존 예약 자신은 충돌 검사에서 제외**해야 한다 — `checkRoom`/`checkStraightRoom`/`checkDayCountLimit`가 공통으로 받는 `seq` 파라미터(9번 참고)가 이 "자기 자신 제외" 용도로 보이나, **아직 실제 변경 흐름으로 라이브 테스트한 적은 없어 확정은 아님** (8번 Open Questions로 별도 기재)
5. 변경 후보를 사용자에게 보여주고 확정 전 확인받음 (신규 예약과 동일하게 확인 후 진행)
6. 확인되면 변경을 실행 — `SaveReserve`가 `reservetype` 값에 따라 수정 모드도 지원하는지, 아니면 `delReserve`(취소) 후 `SaveReserve`(재생성)로 처리해야 하는지는 **미확인** (8번 참고). 후자로 처리할 경우, 재생성이 실패하면 원래 예약이 사라진 채로 남는 위험이 있으므로 재생성 실패 시 원래 예약 정보로 재시도하는 보상 로직이 필요
7. 결과 피드백 (변경 완료 또는 실패 시 원래 예약 유지 여부 안내)
8. **분할 예약(긴 회의) 건의 변경**: "그 3시간짜리 회의 시간 바꿔줘"처럼 대상이 분할 예약이면, 연결된 모든 세그먼트(같은 `reservation_request_id`)를 함께 다룬다는 점을 사용자에게 알리고 진행

### 예약 취소

1. 사용자가 "오늘 3시 회의실 취소해줘"처럼 기존 예약의 취소를 요청
2. Agent가 `bindMyReservation`으로 대상 예약을 특정 — 역시 후보가 여러 건이면 목록을 보여주고 확인받음
3. **분할 예약(긴 회의) 건이면**: 연결된 세그먼트가 여러 개라는 것을 안내하고, "전체 취소"인지 "그중 한 회의실만 취소"인지 확인받음 (기본값을 임의로 정하지 않음 — 취소는 특히 되돌릴 수 없으므로)
4. 확정 전 "OO 회의실 15:00~16:00 예약을 취소할까요?"로 반드시 확인
5. 확인되면 `delReserve(seq)` 호출, DB의 `reservations.status`를 `cancelled`로 갱신
6. 결과 피드백 (취소 완료 안내)

### 예외/분기 상황

- **요청 시간대 충돌**: 요청한 시간대에 예약 가능한 회의실이 없는 경우 → Agent가 대체 가능한 시간대 또는 다른 회의실을 추천
- **인증 실패**: 사내 계정 연동이 안 된 사용자가 요청 → 예약 진행 불가, 안내 메시지 반환
- **미등록/승인 대기 중 사용자가 챗봇 사용 시도**: 온보딩을 마치지 않았거나 Admin 승인 대기 중인 사용자가 예약을 요청 → 예약 진행 불가, 등록 웹페이지 링크 또는 승인 대기 상태 안내
- **외부 시스템 연동 실패**: 사내 예약 시스템 API/세션이 응답하지 않는 경우 → 재시도 또는 실패 안내 (※ 세부 정책은 확인 필요, 8번 참고)
- **범위 밖 요청**: 존재하지 않는 층(예: "10층"), 지원 안 하는 사업장(상암S시티 외), 장비 조건 검색, 한 달 이상의 반복 예약 등을 요청 → 예약을 시도하지 않고 "그건 아직 지원하지 않는다"고 명확히 안내 (아래 "요청 처리 가능 여부 판단" 원칙 참고)

## 3. 도메인 용어 (Ubiquitous Language)

| 용어                              | 의미                                                       | 비고                          |
| --------------------------------- | ---------------------------------------------------------- | ----------------------------- |
| 예약 요청(Reservation Request)    | 사용자가 챗봇에 입력한 목적/날짜/시간대 조건               | 확정 전 상태                  |
| 예약(Reservation)                 | 특정 회의실 + 특정 시간대가 특정 사용자에게 확정 배정된 것 | 자동 확정, 승인 절차 없음     |
| 가용성 조회(Availability Check)   | 요청 조건에 맞는 회의실/시간대가 비어있는지 확인하는 동작  | 사내 예약 시스템 조회 필요    |
| 대체 추천(Alternative Suggestion) | 요청 조건이 불가할 때 Agent가 제시하는 다른 시간/회의실    | 충돌 시에만 발생              |
| 사내 계정(Corporate Account)      | 챗봇 사용자를 식별하는 데 사용하는 사내 인증 정보          | 텔레그램/카카오톡 계정과 매핑 |

## 4. 핵심 엔티티

### User (요청자)

- 설명: 챗봇으로 예약을 요청하는 사내 직원. 온보딩 프로세스(회원가입 신청 → Admin 승인 → 로그인)를 마쳐야 이용 가능
- 주요 속성: 사용자ID, 사내 계정 식별자(email_alias), 암호화된 사내 계정 비밀번호(참조, CJ 자동화 로그인용, 복호화 가능), **앱 로그인 비밀번호 해시(단방향, 이 서비스 자체 로그인용)**, **텔레그램 사용자ID(딥링크로 확보, 위조 불가 — 텔레그램 채널 추가 시 사용, 현재는 미사용)**, 등록 승인 일시, 동의 철회 여부, **선호 회의실 목록(우선순위 순서, 가입 시 입력)**
- 상태(life-cycle): 등록 신청됨(대기) → 승인됨(이용 가능) / 거부됨 → 동의 철회(삭제 요청)

### AccountRegistrationRequest (계정 등록 요청)

- 설명: 사용자가 등록 웹페이지에서 제출한 사내 계정 등록/텔레그램 연동 신청 건. 화이트리스트 미해당 시 Admin의 승인 대상
- 주요 속성: 신청ID, 사내 계정 ID, 암호화된 사내 계정 비밀번호, **앱 로그인 비밀번호 해시**, (텔레그램 채널 추가 시) 텔레그램 딥링크 토큰·연동된 텔레그램 사용자ID, 상태(대기/자동승인/승인/거부), 처리한 Admin(자동승인 시 "system"), 처리 일시
- 상태(life-cycle): 대기(Pending) → 승인(Approved, 수동 또는 자동) / 거부(Rejected)

### AdminWhitelist (Admin 화이트리스트)

- 설명: 가입 즉시 자동으로 Admin 권한을 받는 사내 계정 ID 목록. 별도 승인 절차 없이 Admin 부트스트랩 문제를 해결하기 위한 사전 등록 목록
- 주요 속성: 사내 계정 ID, 등록 사유/등록자, 등록 일시
- 상태(life-cycle): 없음(정적 목록, Admin만 추가/제거 가능)

### Room (회의실) — 개별 예약 단위. 건물/층이 아니라 "회의실 그 자체"를 가리킴

- 설명: 예약 대상이 되는 사내 회의실. 실제 시스템은 **사업장(Site) → 층(Floor) → 회의실(Room)** 3단계 계층으로 관리되며, `Room`은 그중 가장 하위, 실제로 예약되는 최소 단위임
  - 사업장(Site) 예: 상암S시티 (`area_code`, 예: 804) — 1차 범위는 상암S시티로 고정(6번 참고)
  - 층(Floor) 예: 3F, 12F (`sub_area_code`, 예: 1128)
  - **회의실(Room) 예: 3F-1, 12F-3 (`room_code`, 예: 4539)** ← 이 엔티티가 가리키는 대상
- 주요 속성: 회의실명(예: "3F-1"), 소속 층(Floor), 소속 사업장(Site, 1차 범위는 상암S시티 고정), 수용인원 (※ 장비/용도 속성은 1차 범위 제외 — 기본 정보만)
- 상태(life-cycle): 사용 가능 / 사용 중(예약됨)

### Reservation (예약)

- 설명: 특정 Room + 시간대 + User로 구성된 확정 예약 건
- 주요 속성: 예약ID, Room, 요청자(User), 시작/종료 시간, 목적, 상태(확정/취소됨/변경됨)
- 상태(life-cycle): 확정(Confirmed) → 변경됨(Modified) / 취소됨(Cancelled)

### ReservationRequest (예약 요청)

- 설명: 사용자가 챗봇에 입력한 원본 조건(가용성 조회 및 예약 생성의 입력값)
- 주요 속성: 목적, 희망 날짜, 희망 시간대, 요청자
- 상태(life-cycle): 접수 → 가용성 확인 → 확정/충돌

### AlternativeSuggestion (대체 추천)

- 설명: 요청 시간대가 충돌할 때 Agent가 제시하는 대안 목록
- 주요 속성: 추천 Room, 추천 시간대, 원본 요청과의 유사도(우선순위)
- 상태(life-cycle): 제시됨 → 선택됨/미선택

## 5. 엔티티 간 관계

- 한 User는 정확히 하나의 승인된 AccountRegistrationRequest로부터 생성된다 (User는 등록 승인의 결과물).
- AccountRegistrationRequest의 신청 ID가 AdminWhitelist에 존재하면 자동 승인되고, 그렇지 않으면 기존 Admin(User 중 Admin 권한 보유자)의 수동 승인이 필요하다.
- 한 User는 여러 ReservationRequest를 만들 수 있다.
- 한 ReservationRequest는 성공 시 하나의 Reservation으로 이어지거나, 충돌 시 여러 AlternativeSuggestion을 가질 수 있다.
- 한 Room은 여러 Reservation을 가질 수 있으나, 동일 시간대에는 하나의 Reservation만 가능하다(겹침 불가).
- 한 Reservation은 하나의 Room, 하나의 User에 귀속된다.

## 6. 비즈니스 규칙 / 제약조건

- **[결정됨] 요청 처리 가능 여부 판단 (일반 원칙)**: Agent는 어떤 요청이 와도, 도구를 호출하기 전에 먼저 "이게 우리가 정의한 능력과 범위 안의 요청인가"부터 판단한다.
  - 판단 기준 ①: 요청이 정의된 도구(가용성 조회/예약 생성/변경/취소/내 예약 조회 등) 중 하나로 매핑되는가
  - 판단 기준 ②: 알려진 제약 — 상암S시티 고정, 3F·12~16F만 지원, 운영시간 07:00~19:00, 동일회의실 하루 2시간 제한, 예약은 오늘~7일 뒤까지만, 반복 예약 미지원, 장비조건 검색 미지원 — 을 벗어나지 않는가
  - 둘 중 하나라도 아니면 **억지로 시도하거나 결과를 지어내지 않는다**. 범위를 벗어난 게 명확하면 "그건 아직 지원하지 않는다"고 바로 안내하고, 지원 여부가 애매하면(목록에 없는 새로운 표현 등) 추측하지 않고 사용자에게 되물어 확인한다.
  - 이 원칙은 지금까지 정리된 개별 시나리오 목록에 없는, **앞으로 나올 새로운 요청**에도 동일하게 적용되는 상위 원칙이다.
- 예약은 승인 절차 없이 **자동 확정**된다.
- 동일 회의실·동일 시간대에 예약이 이미 존재하면 신규 예약 불가 → 이 경우 **대체 가능한 시간/회의실을 추천**해야 한다.
- 예약의 **변경/취소는 챗봇을 통해 Agent가 직접 처리**한다(별도 시스템 접속 불필요).
- 사내 계정과 연동되지 않은 사용자는 예약을 진행할 수 없다.
- **[변경됨]** 1차 지원 채널은 **웹 챗봇**(React 19, Vercel)이며, 텔레그램/카카오톡은 이후 확장한다 (`prompts/prd.txt` 참고. 기존 계획은 텔레그램 우선이었으나 변경됨 — Vercel Long Polling 제약이 채널 변경으로 해소됨).
- **[확인됨]** 예약 가능 날짜: **오늘부터 7일 뒤까지만** 예약 가능 (매일 하루씩 밀려서 열림). 예: 오늘이 8/12(수)면 ~8/19(수)까지, 하루 지나 8/13이 되면 ~8/20까지
- **[확인됨]** 예약 가능 시간: 07:00 ~ 19:00
- **[확인됨]** 예약 단위: 30분
- **[확인됨]** 1회 최대 예약 시간: 2시간
- **[확인됨]** 같은 사람이 **같은 회의실**을 하루에 여러 번 나눠 잡아도, 합친 시간이 **2시간을 넘으면 시스템이 막는다** (한 번에 2시간이 아니라, "그 사람 + 그 회의실" 기준 하루 합계 2시간 제한). `checkStraightRoom`이 요청 시간보다 넓은 범위까지 확인했던 이유가 바로 이 합산 체크였음
- **[확인됨]** 회의명·내용 입력만으로 예약 가능 (참석자/연락처 등은 필수 아님, 연락처는 사용자 프로필값으로 자동 채워짐)
- **[확인됨]** 참석자/참조자를 추가하지 않으면 사전 알림 메일이 발송되지 않는다 (저장 시 확인 팝업으로 안내됨)
- **[신규 발견]** 1인당 일일 예약 가능 건수에 제한이 있는 것으로 추정됨 (`checkDayCountLimit` 검증 존재, 정확한 제한 수치는 미확인)
- **[결정됨]** 사용자 인증 방식: 사용자에게 **사전 동의**를 받은 뒤, 사내 계정 ID/PW를 **암호화하여 DB에 저장**한다. 로그인(세션 확보) 시점에만 복호화하여 사용하고, 그 외에는 평문으로 노출/로깅하지 않는다.
- **[결정됨]** 모든 예약 요청의 기본 사업장(지역)은 **상암S시티**로 고정한다 (사용자별 소속 추론 불필요, 1차 범위는 상암S시티 단일 사업장).
- **[결정됨]** 사용자는 가입 시 **선호 회의실(우선순위)** 을 등록할 수 있다. 예약 요청이 오면 Agent는 선호 회의실부터 우선 확인한다. **선호 회의실이 전부 예약되어 있으면, 곧바로 예약해버리지 않고 "선호 회의실은 다 찼고, 대신 이런 곳들이 비어있습니다"처럼 우선순위 낮은 곳/선호 목록 밖의 예약 가능한 회의실들을 먼저 리스트업해서 보여준 뒤, 그중에서 사용자가 고르게 한다** (자동으로 아무거나 잡지 않음, "물어봐도 될까요?"처럼 되묻지 않고 바로 대안 목록과 함께 확인받음).
- **[결정됨]** 사용자 등록은 **웹페이지 신청 → Admin 승인** 절차를 거쳐야 하며, 승인 전에는 챗봇을 통한 예약 요청이 불가하다.
- **[결정됨]** 신청 ID가 **Admin 화이트리스트**에 있으면 승인 절차 없이 즉시 자동 승인 + Admin 권한 부여. 그 외에는 등록된 Admin 전원에게 알림 메일 발송 → Admin이 웹 패널에서 수동 승인.
- **[결정됨]** 승인 알림 메일에는 비밀번호(또는 그와 관련된 어떤 정보도) 포함하지 않으며, 메일의 링크는 인증된 Admin 웹 패널로만 연결한다 (메일 링크 클릭만으로 승인되지 않음).
- **[보류 — 텔레그램 채널 추가 시 재적용]** 텔레그램 사용자 신원 확인은 사용자가 채팅으로 자기신고(自己申告)한 값(예: "제 ID는 OOO입니다")을 신뢰하지 않는다. **등록 시점에 텔레그램 딥링크(`t.me/봇?start=토큰`)로 확보한, 위조 불가능한 텔레그램 사용자ID만을 신원 확인 근거로 사용**한다. (지금은 웹 채널이 1차이므로 아래 웹 로그인 규칙이 우선 적용된다.)
- **[결정됨]** 웹 채널의 신원 확인은 **자체 회원가입/로그인(JWT)** 으로 한다. 회원가입 시 CJ 계정 비밀번호(암호화 저장, CJ 자동화용)와 앱 로그인 비밀번호(해시 저장, 로그인 검증용)를 분리해서 저장하며, 둘을 혼용하지 않는다. 로그인은 Admin 승인이 완료된 사용자만 가능하다. 상세는 `prompts/prd.txt` "인증/보안" 참고.

## 7. 바운디드 컨텍스트 (하위 도메인 구분)

- **챗봇 인터페이스 컨텍스트**: 텔레그램/카카오톡 메시지 송수신, 사용자 입력 파싱, 응답 포맷팅
- **예약 도메인 컨텍스트**: 가용성 조회, 예약 생성/변경/취소, 충돌 판정 및 대체 추천 로직
- **외부 연동 컨텍스트**: 사내 예약 시스템(API 또는 세션/쿠키 기반)과의 통신, 인증 연동
- **사용자 인증 컨텍스트**: 챗봇 계정 ↔ 사내 계정 매핑 및 인증 상태 관리
- **계정 등록/관리 컨텍스트**: 등록 웹페이지, Admin 승인/거부 처리, 텔레그램 딥링크 연동 — 챗봇 인터페이스 컨텍스트와는 별도의 웹 화면(Admin용) 필요

- ~~Agent의 사내 계정 인증/세션 확보 방식~~ → **결정됨.** 사용자 동의 후 ID/PW를 암호화 저장, 로그인 시점에 복호화하여 세션 확보 (6번 참고). 다만 아래 구현 세부사항은 여전히 확인 필요:
  - **암호화 키 관리**: 앱 코드/DB와 분리된 KMS(예: AWS KMS, Azure Key Vault 등) 사용 필요. 키와 암호문을 같은 DB에 두면 DB 유출 시 사실상 평문 유출과 동일해짐
  - **세션 만료(~1시간) 대응**: 확인된 세션 유효시간이 짧아, 요청마다 매번 재로그인할지/세션을 캐싱하다 만료 시점에만 재로그인할지 정책 필요
  - **로그인 실패/MFA 트리거 시 처리**: 조건부 액세스(Conditional Access)로 인해 서버발 로그인이 추가 인증을 요구받을 가능성 있음 → 이 경우 사용자에게 알리고 직접 로그인 유도할지 정책 필요
  - **동의 철회 시 즉시 삭제 및 접근 차단 프로세스**
  - **접근 감사로그**: 복호화가 언제, 어떤 요청으로 발생했는지 기록 (평문 자체는 로그에 남기지 않음)
  - **그룹 보안팀/개인정보보호 담당 부서 사전 검토**: 그룹 전체가 쓰는 계정 자격증명을 사내 별도 시스템에 저장하는 것이므로, 법적 근거(개인정보 수집·이용 동의) 및 보안 심사가 선행되어야 함
- `checkDayCountLimit`의 정확한 일일 예약 제한 건수
- ~~`checkStraightRoom`이 요청 시간보다 넓은 범위로 검증하는 이유~~ → **확인 완료.** "동일 사용자 + 동일 회의실"의 하루 누적 시간이 2시간을 넘는지 체크하는 것 (6번 참고)
- 동시에 여러 요청이 같은 시간대를 두고 경쟁할 때의 처리 정책(동시성 제어) — 서버가 처리하는지, Agent가 별도 고려해야 하는지
- 예약 목적 입력값의 형식: 실제로는 "회의명"과 "내용" 두 필드가 필수이며 자유 텍스트임 (챗봇에서 사용자가 입력한 "목적"을 두 필드에 어떻게 나눠 넣을지 정책 필요)
- 외부 시스템 연동 실패 시 재시도 정책 및 사용자 안내 메시지
- **[신규]** 등록 웹페이지 자체의 인증: 직원이 ID/PW를 입력하는 웹페이지를 누구나 접근 가능하게 열어둘지, 사내망 접속 제한을 걸지 결정 필요 (사내 SSO 앞단이라 공개 인터넷에 노출되면 피싱 사이트로 오인/악용될 위험)
- **[신규]** 텔레그램 딥링크 토큰의 보안 속성: 1회용(single-use)인지, 유효시간(만료)이 있는지, 토큰이 유출되면 다른 사람이 가로채 자신의 텔레그램 계정에 연결할 수 있는지 등 설계 필요
- **[신규]** Admin 승인 화면 자체의 접근 통제(누가 Admin인지, Admin 계정 인증 방식)

## 9. 외부 연동 API 명세 (확인됨)

Playwright로 실제 사이트(`cjwappr.cj.net`)에 로그인하여 조회→예약→취소 전체 흐름을 실행하며 확인한 내용. 모두 사내 SSO 로그인 세션 쿠키가 있어야 호출 가능 (공식 API 문서 없음, ASP.NET ASMX 웹서비스).

| 목적                                                   | Method / Endpoint                                          | 주요 요청 파라미터                                                                                                                                                                      |
| ------------------------------------------------------ | ---------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 회의실/층 목록 조회                                    | `POST WSConferenceMain.asmx/listArea`                      | -                                                                                                                                                                                       |
| 날짜별 예약 현황(가용성) 조회                          | `POST WSConferenceReserve.asmx/getDayPilotConfReserveList` | `areaList`(층 코드), `reservedate`, `email_alias`                                                                                                                                       |
| **빈 회의실 추천** (요청 대체 추천에 그대로 활용 가능) | `POST WSConfReserveinsmod.asmx/getEmptyRoomInfo`           | `roomcode`, `startdate`, `starttime`, `endtime`                                                                                                                                         |
| 예약 가능 여부 검증 1                                  | `POST WSConfReserveinsmod.asmx/checkRoom`                  | `area_code`(층코드), `room_code`, `start_date`, `start_time`, `end_time`, `seq`                                                                                                         |
| 예약 가능 여부 검증 2                                  | `POST WSConfReserveinsmod.asmx/checkStraightRoom`          | `area_code`(층코드), `room_code`, `start_date`, `start_time`, `end_time`, `email_alias`, `seq`                                                                                          |
| 일일 예약 건수 제한 검증                               | `POST WSConfReserveinsmod.asmx/checkDayCountLimit`         | `room_code`, `start_date`, `email_alias`, `seq`                                                                                                                                         |

**주의할 점**

- 회의실 위치 식별자가 두 계층으로 쓰이는데 이름이 혼용됨: 건물(`area_code`, 예: 804) / 층(`sub_area_code` 또는 `subarea_code`, 예: 1128) / 회의실(`room_code`). 검증용 API들(`checkRoom` 등)은 층 코드를 `area_code`라는 이름으로 받으므로 구현 시 혼동 주의.
- 조회 응답 인코딩이 UTF-8이 아닌 것으로 보여, 회의실/층 이름의 한글이 깨져서 온다. 클라이언트에서 인코딩 처리 필요.
- 저장 전 `checkRoom` → `checkStraightRoom` → `checkDayCountLimit` 3개 검증을 순서대로 통과해야 `SaveReserve` 호출이 의미 있음 (프론트 로직을 그대로 따라야 함).
- 이 API들은 공식 문서화된 것이 아니라 **실제 브라우저 동작을 관찰하여 역으로 확인한 것**이므로, 사내 IT/인프라팀에 정식 연동 승인 여부를 반드시 확인해야 한다 (8번 Open Questions 참고).
- **[확인됨]** `getDayPilotConfReserveList` 응답의 `reserve_all_list`는 회의실별 30분 단위 문자열이며, **`Y`=이미 예약됨(불가) / `N`=예약 가능(빈 시간)** 이다 (실제 예약 생성 결과로 교차 검증 완료).
- **[해결됨]** `reserve_all_list`가 모든 종류의 "사용 불가"를 반영하지는 않는다(`GUBUN` 0/2 같은 장기 프로젝트성 점유가 `N`(가능)으로 잘못 표시되는 케이스 존재). **해결책 검증 완료**: `reserve_all_list`(그리드) 필터링 결과에 `event_list`의 시간 겹침 검사를 추가로 적용하면 실제 가용성과 정확히 일치한다. 8/13 14:00~15:00, 상암S시티 6개 층(16F/15F/14F/13F/12F/3F) 대상 스캔 결과가 실사용자가 알고 있는 실제 예약 현황(12F 전체 불가, 15F-4·14F-2 예약됨, 3F는 3F-6만 가능)과 100% 일치함을 확인했다. **최종 가용성 판단 알고리즘**: 회의실이 사용 가능하려면 (1) `reserve_all_list`의 해당 시간대 슬롯이 모두 `N`이고, **AND** (2) `event_list`에 해당 회의실(`resource`=room_code)과 시간이 겹치는 항목이 없어야 한다. `GUBUN` 값의 정확한 의미는 몰라도 이 방식이면 무관하게 안전하다.
- **[결정됨]** B1F, 2F 층은 실사용 회의실이 아니므로 회의실 후보 풀에서 항상 제외한다 (1차 범위: 3F, 12F~16F).
- **[신규 발견]** 로그인 세션 유효시간이 토큰상 예상(~1시간)보다 훨씬 짧게(수 분 단위) 끊기는 것을 여러 차례 실제로 관찰함. Agent는 매 요청 전 세션 유효성을 확인하고 즉시 재로그인하는 로직이 사실상 필수이며, "세션 캐싱 후 재사용" 전략은 기대만큼 효율적이지 않을 수 있다.
