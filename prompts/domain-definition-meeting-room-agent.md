# 도메인 정의서 — 회의실 예약 Agent

## 1. 프로젝트 개요
- 서비스 설명: 사용자가 챗봇(텔레그램/카카오톡)에 목적·날짜·시간대를 입력하면, Agent가 사내 회의실 예약 현황을 확인해 가능한 회의실/시간을 안내하고, 사용자 요청에 따라 예약을 자동으로 확정한 뒤 결과를 피드백하는 시스템.
- 주요 사용자(액터):
  - 직원(요청자): 챗봇으로 예약을 요청/변경/취소하는 사람
  - Agent(시스템): 가용성 조회, 예약 확정, 충돌 시 대안 추천, 결과 피드백을 수행하는 주체
  - (참고) 회의실 관리자: 이번 범위에서는 승인 절차 없음(자동 확정) → 별도 액터로 개입하지 않음

## 2. 핵심 업무 프로세스

### 해피 패스
1. 사용자가 챗봇에 목적, 날짜, 시간대(+선호 인원수 등)를 입력
2. Agent가 사내 예약 시스템에서 해당 조건의 가용 회의실/시간을 조회
3. Agent가 가능한 옵션을 사용자에게 안내
4. 사용자가 옵션 중 하나를 선택(또는 확정 요청)
5. Agent가 사내 예약 시스템에 예약을 생성 → 자동 확정
6. Agent가 예약 결과(회의실, 시간, 확정 여부)를 챗봇으로 피드백

### 예외/분기 상황
- **요청 시간대 충돌**: 요청한 시간대에 예약 가능한 회의실이 없는 경우 → Agent가 대체 가능한 시간대 또는 다른 회의실을 추천
- **변경 요청**: 사용자가 기존 예약의 시간/회의실 변경을 챗봇에서 요청 → Agent가 재조회 후 변경 처리 및 결과 피드백
- **취소 요청**: 사용자가 기존 예약 취소를 챗봇에서 요청 → Agent가 취소 처리 및 결과 피드백
- **인증 실패**: 사내 계정 연동이 안 된 사용자가 요청 → 예약 진행 불가, 안내 메시지 반환
- **외부 시스템 연동 실패**: 사내 예약 시스템 API/세션이 응답하지 않는 경우 → 재시도 또는 실패 안내 (※ 세부 정책은 확인 필요, 8번 참고)

## 3. 도메인 용어 (Ubiquitous Language)

| 용어 | 의미 | 비고 |
| --- | --- | --- |
| 예약 요청(Reservation Request) | 사용자가 챗봇에 입력한 목적/날짜/시간대 조건 | 확정 전 상태 |
| 예약(Reservation) | 특정 회의실 + 특정 시간대가 특정 사용자에게 확정 배정된 것 | 자동 확정, 승인 절차 없음 |
| 가용성 조회(Availability Check) | 요청 조건에 맞는 회의실/시간대가 비어있는지 확인하는 동작 | 사내 예약 시스템 조회 필요 |
| 대체 추천(Alternative Suggestion) | 요청 조건이 불가할 때 Agent가 제시하는 다른 시간/회의실 | 충돌 시에만 발생 |
| 사내 계정(Corporate Account) | 챗봇 사용자를 식별하는 데 사용하는 사내 인증 정보 | 텔레그램/카카오톡 계정과 매핑 |

## 4. 핵심 엔티티

### User (요청자)
- 설명: 챗봇으로 예약을 요청하는 사내 직원
- 주요 속성: 사용자ID, 사내 계정 식별자, 챗봇 채널(텔레그램/카카오톡) ID
- 상태(life-cycle): 인증됨 / 미인증

### Room (회의실)
- 설명: 예약 대상이 되는 사내 회의실
- 주요 속성: 회의실명, 위치, 수용인원 (※ 장비/용도 속성은 1차 범위 제외 — 기본 정보만)
- 상태(life-cycle): 사용 가능 / 사용 중(예약됨)

### Reservation (예약)
- 설명: 특정 Room + 시간대 + User로 구성된 확정 예약 건
- 주요 속성: 예약ID, Room, 요청자(User), 시작/종료 시간, 목적, 상태(확정/취소됨/변경됨)
- 상태(life-cycle): 확정(Confirmed) → 변경됨(Modified) / 취소됨(Cancelled)

### ReservationRequest (예약 요청)
- 설명: 사용자가 챗봇에 입력한 원본 조건(가용성 조회 및 예약 생성의 입력값)
- 주요 속성: 목적, 희망 날짜, 희망 시간대, 요청자
- 상태(life-cycle): 접수 → 가용성 확인 → 확정/충돌

### AlternativeSuggestion (대체 추천)
- 설명: 요청 시간대가 충돌할 때 Agent가 제시하는 대안 목록
- 주요 속성: 추천 Room, 추천 시간대, 원본 요청과의 유사도(우선순위)
- 상태(life-cycle): 제시됨 → 선택됨/미선택

## 5. 엔티티 간 관계
- 한 User는 여러 ReservationRequest를 만들 수 있다.
- 한 ReservationRequest는 성공 시 하나의 Reservation으로 이어지거나, 충돌 시 여러 AlternativeSuggestion을 가질 수 있다.
- 한 Room은 여러 Reservation을 가질 수 있으나, 동일 시간대에는 하나의 Reservation만 가능하다(겹침 불가).
- 한 Reservation은 하나의 Room, 하나의 User에 귀속된다.

## 6. 비즈니스 규칙 / 제약조건
- 예약은 승인 절차 없이 **자동 확정**된다.
- 동일 회의실·동일 시간대에 예약이 이미 존재하면 신규 예약 불가 → 이 경우 **대체 가능한 시간/회의실을 추천**해야 한다.
- 예약의 **변경/취소는 챗봇을 통해 Agent가 직접 처리**한다(별도 시스템 접속 불필요).
- 사내 계정과 연동되지 않은 사용자는 예약을 진행할 수 없다.
- 1차 지원 채널은 **텔레그램**이며, 카카오톡은 이후 확장한다.

## 7. 바운디드 컨텍스트 (하위 도메인 구분)
- **챗봇 인터페이스 컨텍스트**: 텔레그램/카카오톡 메시지 송수신, 사용자 입력 파싱, 응답 포맷팅
- **예약 도메인 컨텍스트**: 가용성 조회, 예약 생성/변경/취소, 충돌 판정 및 대체 추천 로직
- **외부 연동 컨텍스트**: 사내 예약 시스템(API 또는 세션/쿠키 기반)과의 통신, 인증 연동
- **사용자 인증 컨텍스트**: 챗봇 계정 ↔ 사내 계정 매핑 및 인증 상태 관리

## 8. 확인이 필요한 사항 (Open Questions)
- **사내 예약 시스템 연동 방식**: 공식 API 제공 여부 확인 필요. API가 없다면 세션/쿠키 기반 접근(스크래핑 방식) 가능 여부 및 안정성 검토 필요
- **사내 계정 연동 방식**: SSO/사번 인증 등 구체적인 인증 방식 확정 필요
- 회의실 운영 시간(예: 09:00~18:00) 및 예약 가능한 최소/최대 시간 단위
- 동시에 여러 요청이 같은 시간대를 두고 경쟁할 때의 처리 정책(동시성 제어)
- 예약 목적 입력값의 형식(자유 텍스트 vs 카테고리 선택)
- 외부 시스템 연동 실패 시 재시도 정책 및 사용자 안내 메시지
