PRD — 회의실 예약 Agent

(상세 도메인 설계는 prompts/1-domain-definition-meeting-room-agent.md 참고. 이 문서는 그걸 보완하는 비즈니스/기술/프로젝트 관리 정보다.)

## 1. 비즈니스 관련 정보

- 배경: CJ프레시웨이 임직원은 업무 특성상 미팅이 매우 잦고, 인원수/시간대에 맞는 회의실을 그때그때 빠르게 잡아야 한다. 지금은 예약 화면을 열어 층마다 눈으로 비어있는 곳을 확인하고 직접 타이핑해서 저장해야 해서 번거롭고, 이 지연이 실제 업무를 하루이틀 늦추는 경우도 있다.
- 목표: 챗봇에 자연어 요청("내일 오후 2-3시 8명 회의실")만 하면 Agent가 사내 회의실 예약 시스템을 대신 조회·예약해주는 서비스를 만든다. **1차 채널은 웹 챗봇(React 웹앱)이며, 텔레그램은 추후 확장한다** (기존 계획은 텔레그램 우선이었으나 변경됨).
- 대상 사용자: CJ프레시웨이 임직원 (1차 범위: 상암S시티 사업장 소속/이용자만)
- 기대 효과: 회의실 확인·예약에 걸리는 시간을 수 분에서 수십 초로 단축, 규칙(2시간 제한 등)을 몰라서 예약이 실패하는 경우 제거
- 비용 관점: LLM 호출량이 대화당 수 회 수준으로 많지 않을 것으로 예상 (OpenAI 저비용 모델 사용, 3번 참고)

## 2. 기술 제약사항

### 환경별 인프라

| | Dev (개발) | Prd (운영) |
| --- | --- | --- |
| 프론트엔드 | 로컬 PC (Vite dev) | **사내 전용 노트북** (백엔드가 같은 포트에서 서빙) |
| 백엔드 | 로컬 PC | **사내 전용 노트북** (Node 상시 프로세스) |
| DB | **로컬 PC(Postgres, 별도 설치)** | **Supabase** |

- **[2026-08-19 결정 변경 — Vercel 폐기]** 운영 환경을 Vercel에서 **사내 전용 노트북**으로 바꿨다.
  - **이유**: **CJ 예약 시스템(`cjwappr.cj.net`)이 사내망에서만 접근 가능하다.** 실제로 Vercel에 프론트/백엔드를 배포해 `/health`(Supabase 왕복)까지 성공시켰지만, CJ 자동화는 클라우드에서 원천적으로 불가능하다는 것이 확인되어 폐기했다. 이 서비스의 핵심 가치가 CJ 예약이므로 "예약이 안 되는 배포"는 의미가 없다.
  - 검토했던 대안: ① 하이브리드(Vercel 웹 + 사내 워커가 작업 큐 폴링) — 큐/워커/비동기 채팅 흐름을 새로 만들어야 해 이 규모에 과하고, 결국 예약 기능의 사내 PC 의존은 남는다. ② 사내 서버(VM) 정식 배포 — 기술적으로 가장 깔끔하나 IT 승인 절차가 필요. **나중에 사내 서버가 생기면 ②로 옮기는 것이 정답이고, 그때 이 노트북 구성을 그대로 이식하면 된다.**
  - **DB는 Supabase를 그대로 쓴다.** 사내망에서 Supabase로 아웃바운드 접속이 가능함을 실측 확인했다(Session pooler 5432 / Transaction pooler 6543 모두 성공, Direct 연결은 IPv6 전용이라 실패). 노트북이 고장나도 데이터는 안전하며, 노트북은 언제든 교체 가능한 "실행 기기"가 된다.
  - **운영 세팅 절차는 `docs/laptop-server-setup.md`가 정본이다.**
- **[2026-08-18 결정] Dev/Prd DB 분리**: Dev(로컬 PC)는 로컬에 직접 설치한 Postgres를 쓰고, Prd만 Supabase에 연결한다.
  - **이유**: 로컬 개발 중에는 반복 예약 스케줄러 수동 실행, 실사용 데이터 조작 등 실험적인 DB 조작이 잦다 — 이걸 실제 Supabase(실사용자 데이터가 쌓일 곳)와 공유하면 개발 중 실수가 운영 데이터를 오염시킬 위험이 있다. 로컬 PC가 사내망에 없거나 인터넷이 끊겨도 개발이 가능해야 한다는 점도 있다.
  - **트레이드오프**: 로컬 Postgres와 Supabase(Prd)의 스키마가 어긋나지 않도록 `supabase/migrations/`의 모든 마이그레이션을 **양쪽에 동일하게** 적용해야 한다 — 마이그레이션 파일을 새로 추가할 때마다 로컬 `psql`과 Supabase(MCP 또는 대시보드) 양쪽에 적용하는 걸 원칙으로 한다. 세션 타임존처럼 두 환경이 실제로 다를 수 있는 값(`5-project-principle.md` 41번 참고)에도 더 신경 써야 한다.
- **프론트/백엔드는 한 프로세스, 한 포트(3000)로 돌린다.** 백엔드(Express)가 `frontend/dist`를 함께 서빙한다(`backend/src/app.ts`). 자동 시작/감시 대상이 하나로 줄고, same-origin이라 Refresh Token 쿠키(`SameSite=Lax`)와 CORS 설정이 그대로 동작한다. `/admin`·`/chat`은 프론트 페이지 경로와 API 프리픽스 이름이 겹치므로 `Accept: text/html` 여부로 페이지 이동과 fetch 호출을 구분한다.
- **Supabase 무료 플랜 주의**: 7일간 요청이 없으면 프로젝트가 자동 일시정지된다. 노트북이 상시 가동되면 스케줄러가 매일 DB를 건드리므로 문제없지만, 장기 연휴로 오래 꺼두면 복귀 후 대시보드에서 수동 복구가 필요할 수 있다. 자동 백업도 무료 플랜에는 없다.

### 인프라 제약

- 프론트엔드: **React 19**. 전역 상태관리는 **Zustand** 사용. 백엔드와의 통신은 **TanStack Query**로 처리.
  - 대상 화면: 계정 등록 웹페이지, Admin 승인 패널, **웹 챗봇 UI**(1차 채널) — 전부 React 19. 운영에서는 `vite build` 산출물을 백엔드가 같은 포트에서 서빙한다.
  - **[결정됨] 4개 화면 모두 반응형(모바일/태블릿 포함)으로 설계한다.** 사내 직원이 PC뿐 아니라 휴대폰으로도 접근할 수 있어야 하므로, 고정폭 데스크톱 전용 레이아웃으로 만들지 않는다 (`prompts/7-wireframes.md` 참고).
- 백엔드: **Node.js + Express**, 사내 노트북에서 **상시 프로세스**로 구동(`npm start` → `dist/src/app.js`). DB 접근은 Supabase의 자동 생성 REST API가 아니라 **`pg` 라이브러리로 Postgres에 직접 연결**하는 방식을 쓴다.
  - 참고: DB는 Supabase(Postgres) 그대로 사용하되, RLS 설계상 서버는 service role 수준 권한으로 접근하는 걸 전제로 하고 있어 `pg` 직접 연결 방식과 궁합상 문제없다 (`supabase/migrations/20260813000900_rls.sql` 참고).
  - 대상: 등록/Admin 승인 API, 웹 챗봇 API, CJ 자동화 모듈 — 전부 이 Express 백엔드 위에서 동작
  - **커넥션은 Supabase 풀러를 경유한다.** 상시 프로세스라 서버리스처럼 커넥션이 폭증하진 않지만, Supabase의 Direct 연결(`db.<ref>.supabase.co:5432`)은 **IPv6 전용이라 사내망에서 DNS 해석부터 실패한다**(2026-08-19 실측). 따라서 풀러 주소를 쓰는 것이 선택이 아니라 필수다 — 상시 프로세스에는 **Session pooler(5432)**, GUI 도구(DBeaver 등)도 같은 주소를 쓴다.
- LLM: **OpenAI API**, 가장 저렴한 모델(`gpt-5-nano`, `.env`의 `OPENAI_MODEL` 참고). 도구 호출(tool-calling) 정확도가 부족하면 상위 모델(`gpt-5-mini`)로 교체 가능하도록 모델명을 환경변수로 분리해둠.
- CJ 사내 예약 시스템 연동: 공식 API 없음, Playwright 기반 로그인 + 비공식 ASMX 웹서비스 호출 (`1-domain-definition-meeting-room-agent.md` 9번 참고). **사내 노트북에 설치된 일반 Playwright Chromium으로 실행**한다(`npx playwright install chromium`).
  - **[2026-08-19 확정된 제약] CJ 시스템은 사내망에서만 접근 가능하다.** 이것이 운영 환경을 클라우드가 아닌 사내 노트북으로 정한 결정적 이유다(위 "환경별 인프라" 참고). 어떤 외부 호스팅을 쓰든 CJ 자동화는 사내망 안에서 실행되어야 한다.
  - `@sparticuz/chromium`(서버리스 전용 경량 크로미움) 분기는 `cj-automation/session.ts`에 남아 있지만, 사내 노트북 구성에서는 타지 않는다(`isServerlessEnv()`가 false). 향후 사내 서버 컨테이너 배포 등으로 다시 필요해질 수 있어 코드는 유지한다.
  - CJ 사내 세션이 수 분 단위로 짧게 끊기므로, 상위 계층은 세션 상태를 알지 못하고 CJ 자동화 계층이 매 요청 유효성 확인 후 필요하면 재로그인한다.
  - **[리스크]** 응답 지연: 요청마다 헤드리스 브라우저를 새로 띄우므로 응답까지 몇 초가 걸릴 수 있다. 챗봇 UI에 "처리 중" 표시(로딩 인디케이터)를 반드시 넣어 사용자가 멈춘 것으로 오해하지 않게 한다.
  - **[리스크/미검토]** 여러 사용자가 동시에 예약을 요청하면 헤드리스 브라우저 여러 개가 동시에 CJ 사내 시스템에 로그인을 시도하게 된다. CJ 시스템이 이런 동시 접속 패턴을 이상 트래픽으로 감지해 차단할 가능성은 아직 검토된 바 없다 — 실사용 트래픽이 생기면 확인 필요.

### 반복 예약 스케줄러 인프라

- **[결정됨]** 스케줄러 호스트: **Windows 작업 스케줄러(사내 전용 노트북 — 웹 서버와 같은 기기)**
  - 근거: 자정(00:01)에 분 단위로 정확히 실행되어야 하는데, 클라우드 크론은 그 정밀도를 보장하지 않는 경우가 많다. 무엇보다 이 잡은 CJ에 실제 예약을 넣으므로 **사내망 안에서 실행되어야만 한다**(위 CJ 접근 제약 참고).
  - **[중요] 작업에 `StartWhenAvailable`을 반드시 켠다.** 노트북이 00:01에 꺼져 있었다면 켜진 직후 놓친 실행을 따라잡게 하는 옵션이다. 이게 없으면 그날 예약이 통째로 사라진다 — 2026-08-19에 실제로 발생했다(`LastTaskResult`가 `0x800710E0` = 제약 조건으로 미실행). 절전/최대 절전을 끄고 전원 어댑터를 상시 연결하는 것도 같은 이유로 필수다.
  - 실행 주기: **매일 자정(00:01)**
  - 실행 대상: 등록된 모든 반복 예약 규칙 (사용자별 순차 실행, 병렬 실행 금지)
- **[미결]** CJ의 +7일 예약 창이 정확히 자정(00:00 또는 00:01)에 열리는지 확인 필요 (도메인 정의서 §6 참고)
- **[한계]** 스케줄러를 실행하는 Windows PC의 조건:
  - 항상 켜져 있어야 함 (절전 상태도 불가)
  - 항상 사내망(VPN)에 연결되어 있어야 함
  - PC가 꺼지거나 절전 상태면 그날 반복 예약은 실패하며, 수동 복구 수단은 없음 — 이는 이 기능의 근본적 한계다

### 인증/보안 (자체 로그인)

이 서비스 자체(웹 챗봇/등록 웹페이지/Admin 패널)에 로그인하는 방식이며, CJ 사내 SSO 자격증명(사용자가 등록 시 입력하는 **CJ WORLD ID / CJ WORLD PW**, Playwright 자동화용으로 암호화 저장되는 것)과는 **별개**다. 혼동하지 않도록 문서 전체에서 구분해서 사용한다.

**[결정됨 20260816] 사용자에게 보이는 명칭은 "CJ WORLD ID" / "CJ WORLD PW"로 통일한다.** 이전에는 "사내 계정 ID/비밀번호"라고 불렀는데, 앱 로그인 비밀번호와 헷갈린다는 실사용 피드백이 있었다. DB 컬럼명(`email_alias`, `encrypted_password`)은 그대로 두고 **UI 문구와 사용자에게 보이는 에러 메시지만** 바꾼다.

- **[결정됨] 별도의 웹 회원가입/로그인 페이지가 필요하다.** 원래 도메인 설계는 텔레그램 딥링크로 신원을 확인했지만, 1차 채널이 웹으로 바뀌면서 "승인된 사용자가 재방문 시 어떻게 로그인하는가"가 비어있었던 문제(직전 PRD 검토에서 발견)를 이걸로 해소한다.
  - **회원가입**: 기존 "등록 웹페이지"(CJ WORLD ID/PW + 선호 회의실 신청)에서, **이 앱 전용 로그인 비밀번호도 함께 설정**한다. CJ 비밀번호와 앱 로그인 비밀번호는 별개의 값이며 별도로 저장한다(앱 로그인 비밀번호는 해시로 저장 — CJ 비밀번호처럼 복호화가 필요한 게 아니므로 bcrypt/argon2 같은 단방향 해시를 쓴다. CJ 비밀번호의 "복호화 가능한 암호화" 방식과 혼동하지 않는다).
  - 회원가입 제출 자체는 anon(비로그인) 상태의 공개 폼이라 인증이 필요 없다(RLS 설계와 일치). **로그인은 Admin 승인이 완료된 이후부터 가능**하다.
  - **로그인 페이지**: 승인된 사용자가 앱 로그인 비밀번호로 로그인 → 위 JWT(access+refresh) 발급. 이후 웹 챗봇 UI 접근은 이 로그인 세션을 전제로 한다.
  - Admin 패널 로그인도 동일한 회원가입/로그인 체계를 그대로 쓴다(Admin 권한 여부만 `users.is_admin` 같은 플래그로 구분).
- **JWT 기반, Access Token + Refresh Token 둘 다 사용**한다.
  - **Access Token**: 짧은 만료(예: 15분). 매 API 요청의 인증에 사용. 클라이언트에서는 메모리(Zustand 등)에만 두고 localStorage에는 저장하지 않는다 (XSS로 탈취되면 바로 사용 가능한 토큰이라 저장 위치가 중요).
  - **Refresh Token**: 긴 만료(예: 7~30일, 구체 값은 추후 확정). **httpOnly + Secure + SameSite 쿠키**로만 저장 — 브라우저 JS가 직접 읽을 수 없게 해서 XSS로 인한 탈취 위험을 낮춘다. Access Token이 만료되면 이 토큰으로 재발급 전용 엔드포인트를 호출해 새 Access Token을 받는다.
  - Refresh Token도 만료되거나 로그아웃/폐기되면 재로그인이 필요하다.
- **폐기(로그아웃/보안사고 대응) 가능해야 함**: JWT 자체는 stateless라 발급 후 서버가 강제로 무효화할 수 없으므로, Refresh Token은 DB에 발급 이력을 남겨 **서버 쪽에서 개별/전체 폐기(revoke)** 가 가능한 구조로 설계한다 (Access Token은 만료 시간이 짧아 최악의 경우도 노출 시간이 제한적이라 별도 폐기 목록은 두지 않음).
- 로그인이 필요한 화면(웹 챗봇 UI, Admin 패널)은 **모두 동일한 인증 방식**을 사용한다. 등록 웹페이지의 "신청 제출" 자체는 로그인 전 공개 폼이라 예외다.
- 상세 구현(토큰 만료 시간 정확한 값, 재발급 흐름의 동시성 처리, Refresh Token 저장 테이블 스키마 등)은 실제 구현 단계에서 확정 — 지금은 방식(JWT, access+refresh 이중 토큰)만 확정.

#### [결정됨 20260816] 비밀번호 변경 — 두 비밀번호 모두 사용자가 바꿀 수 있어야 한다

CJ WORLD PW는 사내 정책상 주기적으로 만료된다. 사용자가 CJ에서 비밀번호를 바꾸면 우리가 보관 중인 암호문이 낡은 값이 되어 CJ 로그인이 전부 실패하고, **앱 전체가 그 사용자에게 멈춘다.** 재등록 수단이 없으면 `email_alias`가 unique라 재가입도 막혀서, 시간이 지날수록 사용자가 하나씩 잠기는 구조가 된다. 그래서 비밀번호 변경은 편의 기능이 아니라 **필수 복구 경로**로 취급한다.

- **CJ WORLD PW는 저장 전에 실제 CJ 로그인으로 검증한다.** 검증 없이 저장하면 오타 하나로 이후 모든 동작이 죽는데 사용자는 원인도 모르고 되돌릴 수도 없다. 검증에 성공한 값만 저장하고, 옛 비밀번호로 맺어둔 CJ 세션 캐시는 즉시 버린다. 브라우저 자동화라 응답이 수 초 걸리는 것을 UI가 감안해야 한다.
- **복구 경로는 로그인 전에도 열려 있어야 한다.** 로그인 시점에 CJ 세션을 함께 확보하고 **실패하면 로그인 자체를 거부**하도록 되어 있어(틀린 CJ 자격증명으로도 앱에 들어와지던 문제를 막으려고 의도적으로 넣은 동작), 인증된 화면 안에만 재등록 기능을 두면 **정확히 그게 필요한 상황에서 도달할 수 없다.** 따라서 경로를 둘로 나눈다:
  - 로그인 상태 — `PATCH /me/cj-world-password` (만료 전 미리 변경)
  - 로그인 불가 상태 — `POST /auth/cj-world-password` (JWT 대신 **앱 로그인 비밀번호로 본인 확인**, 로그인 화면에서 `CJ_LOGIN_FAILED`일 때만 노출)
- **앱 로그인 비밀번호 변경**(`PATCH /me/app-password`)은 현재 비밀번호를 확인한 뒤에만 교체하고, 성공 시 해당 사용자의 Refresh Token을 **전부 폐기**해 기존 세션을 끊는다. 새 비밀번호는 8자 이상.
- **[미결] 비밀번호 분실 시 재설정은 아직 불가능하다** — 메일 발송 기능이 없어서 자가 재설정 흐름을 만들 수 없다. 현재는 Admin이 대신 처리하는 방법뿐이며, 메일러 도입 여부는 별도 결정 필요.
- **[미결] 이 경로들에는 rate limit이 없다** — 틀린 CJ WORLD PW를 반복 시도하면 실제 CJ 계정 잠금 정책을 자극할 수 있다.
- **[미결] 가입 시점에는 앱 비밀번호 최소 길이 규칙이 없어** 변경(8자)과 불일치한다. 가입 쪽에도 같은 규칙을 넣을지 결정 필요.
